# Output contract

For each assigned scenario, write exactly these five files in the controller's assigned case directory. Existing outputs from another arm are not inputs.

1. `executive.md`: identify the exact outcome and methodology basis; the supplied subject/currentness facts; selected next frontier and its reason; proposed role/authority/read/write bindings; retained obligations, affected prior evidence and blocked successors; exact information that would allow a different continuation; and the consumer of each return. Cite scenario fact IDs and acquired method sources. Distinguish a proposed frame from an admitted or executed activation. Include a concise human-readable map of the decisive dependencies/constraints, consistent with constraint-map.json.
2. `worker.md`: a readable recipient context sufficient for the selected bounded work, or a specifically inactive/blocked context. Bind the desired result, necessary source and dependency meaning, applicable requirements/design, permitted inputs/effects, exclusions, proof predicates, result destination and stop/return boundary. Keep unavailable facts explicit. This file must stand on its own with its exact qualified references; it must not require reading the Executive's private reasoning.
3. `reviewer.md`: a readable review context for the selected subject and claim, conditional on a named candidate/result where necessary. Bind governing expectations, allowed evidence, read/write limitations, prior exposure, actual independence conditions, expected finding/result form and return consumer. It is not a performed assessment. If no review is required for the selected frontier, explain that standing and the condition under which this proposed context would apply.
4. `constraint-map.json`: a small graph explaining the generated contexts. Top-level keys are `schema` (`stdo.context-generation.constraint-map/1`), `scenario`, `nodes`, `edges` and `limitations`. Each node has a stable `id`, `kind` (`method_fact`, `scenario_fact`, `inference` or `context_decision`), readable `text`, and `source_refs`. Each edge has `from`, `to`, a meaningful explicit `type`, a short `reason` and `source_refs`. Use source references that resolve to a supplied fact ID or an exact acquired method path/section/record identity. An inference names its premises and remains an inference; an edge must explain a real dependency or decision, not just keyword proximity. This map describes your output, not formal verification.
5. `acquisition.json`: schema `stdo.context-generation.acquisition/1`, scenario, assigned mode, actual Skill path/hash, exact method/model identities used, and an ordered `acquisitions` array. Record actual tool/query or file read, source path/locator, hash when known, range/record IDs, purpose and bytes returned/read when observable. Record fallback sources and reasons, failed reads and any supplied preverified identity separately from checks actually performed. Include `metrics` with known acquired-byte totals, query/read counts, generated output file bytes, observed elapsed time, token/cost measures only if exposed, and explicit unavailable fields. Do not substitute whole-file size for a partial acquisition, count cached input as a separate additive token population, or claim mental attention was measured.

A qualified source reference can use an exact local immutable path plus file SHA-256 and line range/heading, or an exact model identity plus record identity and its source grounding. A scenario source reference uses the brief path/hash plus fact ID. You may use a short source table to avoid repeating long provenance throughout the readable contexts. No invented physical file hashes for fictional coordinates.

The evaluator will consider relevant constraint coverage, material omissions, contradictions, authority/currentness/continuation preservation and how easily a reader can follow the contexts and their source grounding. Input bytes/queries and output bytes are proxies, not actual consumer performance. A smaller output that drops a decisive distinction is not an improvement.
