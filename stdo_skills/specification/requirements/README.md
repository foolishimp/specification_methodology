# STDO Skills requirements

| ID | Required behavior |
|---|---|
| SK-01 | Both host bindings expose the exact selected native core workflows and preserve their relative references. Irrelevant work is not forced through an STDO pipeline. |
| SK-02 | Resolve one selected Product/method and verify the exact install; missing, ambiguous or changed identities withhold dependent operations. |
| SK-03 | Preserve existing grants, direct Writer sufficiency, native work ownership and source-defined coordination/review boundaries. |
| SK-04 | Invoke real supported public operations; retain failures and partial effects without fabricated success. |
| SK-05 | Use the independent Purpose Context Product for relevant task constraints; prefer a matching existing purpose index before scoped new authoring. |
| SK-06 | Preserve exact purpose, task facts, source/method identity and unknown applicability; stale source and purpose mismatch refuse index reuse. |
| SK-07 | Keep source-first independent review independent of candidate-derived indexes and answers. |
| SK-08 | Re-entry reacquires actual state and evidence; prior passing observations do not survive material drift automatically. |
| SK-09 | Report code/transport/semantic coverage/authority and performed/unperformed checks separately. |
| SK-10 | Install an exactly inventoried development or explicit release package with independently pinned components. Release mode binds its actual native cut, Product identity and version; development mode acquires no release standing. |
| SK-11 | Verify/remove only exact receipt-owned roots; preserve unrelated files and other installs. |
| SK-12 | Keep actual automatic host pickup, explicit invocation and local command execution as separate claims. |
| SK-14 | When explicitly selected, provide visual project/code documentation through the visual Product; no Lean or formal/context prerequisite. |
| SK-15 | Supply the adopted SDLC default at relevant work, QA, triage, repair and boundary decisions through the independently owned purpose index and original-source routes. |
| SK-16 | Preserve outcome, basis, scope and decision boundaries across review and refresh; material drift receives causal triage and lawful re-entry. |
| SK-17 | Support evidence-based repair termination and affected-claim rechecks while preserving required independence, acceptance gates and reusable valid evidence. |
| SK-18 | Demonstrate these behaviours through actual bounded consumer scenarios; distinguish explicit development-source selection, installed workflow, host pickup and release qualification. |
| SK-19 | Carry constitutional ticket/work-state authority and bounded context/restart duties through the native Skills and shared Purpose Context route. Bind the current sufficient carrier, actual source/evidence, qualified references and declared acquisition envelope; persist required results through the granted route. A guide, summary, index or new actor cannot replace that state, create a write grant or reset completed work. |
| SK-20 | Demonstrate continuation without inherited conversation, contrary stale-account correction, affected-evidence reuse, uncertain-effect restraint and capacity-bounded acquisition. Preserve lawful no-new-ticket work and role-specific result updates; do not infer behavior from installed words alone. |

The old registry-based SK-13 and formal support composition were withdrawn by the
owner's scope change. Their bytes/evidence remain historical, not satisfied by
renaming them. [Purpose index consumption](PURPOSE-INDEX-CONSUMPTION.md) defines
the current cross-Product use; [scenarios](SCENARIOS.md) define finite evidence.
