## Product boundary

Product identity: `urn:stdo:product-definition:stdo-skills`.
Bounded context: `urn:stdo-skills:bounded-context:agent-method-application`.

The Product supplies skills for F_P agents applying an exactly selected STDO
methodology to software-development work. It connects recognizable user tasks
to the deciding source, appropriate context, supported tool operations and
observable returns. It owns requirements for this user-facing capability and
evidence that each tenant realizes it.

STDO owns the method. a_c and other declared Development Products own their tool
contracts and computational implementations. A skill preserves and applies those
contracts; it does not create another lifecycle, state store or source of
assessment, admission, acceptance or publication authority.

The [selected a_c composition relation](composition/A_C_SUPPORT.md) binds the
construction dependency and exact provider source. SK-13 applies scoped edge
resolution and eligible context at the existing lifecycle points; it adds no
mutable methodology dependency or alternate authority owner.

## Users and capability

The user works in a governed workspace using Codex or Claude. Skills support:

- setup and exact Product/method selection;
- intake and re-entry at the changed requirement, design or realization owner;
- context acquisition and bounded frame construction;
- authorized direct work or Executive-directed delegation;
- source-first independent review where required;
- continuation, recovery, currentness and truthful status;
- release preparation and separately authorized release operations.

The shared requirements state outcomes and discriminators. They do not prescribe
skill count, names, prompt identity, invocation syntax or host-specific mechanism.
Each tenant owns its computational and execution binding, including instructions,
supporting references, tool integration, installation and tuning.

## Tool relationship

The current `stdo` manager verifies and resolves the exact installation. The
separately implemented native a_c 3.0.1 profile supplies the selected public
acquisition, context, preflight, dispatch, Writer and evidence/return operations.
Its [owning design](../../a_c/build_tenants/graphify/design/fd-support-stdo-3.0.1.md)
states the supported fragment; native `results.conjoin` remains unsupported.
The legacy RC9 profile and its provenance remain distinct. Each operation's
supported claim follows its exact contract and actual evidence, not a label or
blanket calculus-conformance claim.

Tool harmonisation remains owned by a_c. This Product may identify required
contracts, report defects and consume a supported increment; it does not fork
tool semantics into each tenant. A skill's direct use of host facilities must
be declared in its design, preserve the selected operation contract and be
qualified on that actual path. It cannot substitute for a required tool result.

F_D classification follows the selected calculus's totality and dependency
requirements. An F_D constructor gains no assessment or admission authority from
that classification; invoking an F_P actor does not make its semantic answer
deterministic. The deciding owners are in [SOURCE_OWNERS.md](SOURCE_OWNERS.md).

## Independent tenants and releases

`build_tenants/codex/` and `build_tenants/claude/` independently realize the common
WHAT. Evidence and supported-host claims are tenant-specific. Both use the same
task semantics and acceptance predicates, while host realization and tuning may
differ materially. Common machinery is reused where its contract fits; retained
variants need a concrete supported difference.

This Product is a peer at the monorepo root. It has its own lifecycle and release
identity and is not automatically a member of an existing STDO release cohort.
The present work constructs candidates and performs bounded qualification; it
does not publish a release or install skills into unrelated user environments.

## Acceptance boundary

Initial delivery requires a coherent common specification, both realized tenant
designs, usable host installation paths, supported tool bindings, and independent
assessment of the [finite scenario evidence](requirements/SCENARIOS.md).
Missing or failed mandatory evidence withholds the corresponding supported claim.
It cannot be hidden by a suite total or by the other tenant succeeding.

Repeated use may establish broader reliability and benefit. This first experiment
supports only the cases, hosts, settings, tool versions and outcomes actually
observed. Product acceptance and release remain owner decisions on that evidence.
