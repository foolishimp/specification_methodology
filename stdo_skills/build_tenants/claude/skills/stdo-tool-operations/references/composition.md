# Product composition at the context boundary

Use this route when the selected task consumes another Product or the activation
requires a composition-controlled view. The target's exact installed methodology
still governs. Skills' construction uses its own selected `A_C_SUPPORT` relation
under installed STDO 3.0.1; mutable successor method source is not a runtime input.

## Resolve the declared dependency

Select the Product definition, exact source/provider contract and permitted
resolver boundary from the activation. The manager implementation must support
composition verification; the older global `stdo` 0.1.5 can return green without
checking edges. Use the declared candidate source/interpreter or an installed
successor whose capability has been established:

```sh
PYTHONPATH="$STDO_MANAGER_SOURCE" "$STDO_MANAGER_PYTHON" -B -m stdo_toolchain.cli \
  fleet verify --root "$PRODUCT_DEFINITION" --resolver-root "$RESOLVER_ROOT"
```

`STDO_MANAGER_SOURCE` locates the selected `stdo_toolchain` package's parent,
currently `specification_methodology/v2/src` inside the declared tool checkout.
Other variables bind its interpreter with dependencies, the selected definition
and the authorized local resolution boundary. Do not broaden that boundary just
to get green or assume every adjacent Product is selected. The command follows
only declared targets; a sibling dependency needs an explicitly permitted root.

Retain actual diagnostics. Require the supported `stdo.composition-verification`
report/schema1 and inspect per-edge identity/reference failures. A valid mechanical
result explicitly leaves `authority_and_semantic_adequacy` not evaluated. It does
not authorize acquisition, grant a child rights or establish a sufficient context.
Unsupported URI/fragment forms or older CLI behavior leave the relevant check open.

## Inspect and use the actual trusted binding

Discover `composition.inspect` through `tools.describe` on the selected native
a_c implementation. The inspection request uses the ordinary CLI/MCP envelope:

```json
{"schema":"a_c.fd-support.request/1","id":"composition-inspect-unique","operation":"composition.inspect","arguments":{}}
```

Use a fresh actual request identity and the activation's exact policy/digest and
principal. The composition declaration is a SourceRef registered by the trusted
operator policy; it is not a request field that the actor can replace. Inspect
whether a binding is selected, its exact declaration/source identity, engagement,
purpose, actor and route, allowed resources and limits. No selected binding means
no claim that this optional guard is active. If the task requires it, withhold
that dependent claim/action and return the missing operator binding.

Use the same declared routes for `source.read`, selected context assembly,
preflight and delivery. A local successful inspection is not evidence that a later
read or child handoff was checked. Retain actual acquisition/effect evidence and
consume refusals on the actual path. Do not replace absent guard support with a
narrative assertion or a different profile relabeled as equivalent.

## Select information and preserve the continuation

Keep the outcome-owning Product, local versus integrated predicate, exact basis,
existing authorities, material dependencies, required evidence and open obligations.
Enter an intermediate Product using its own admitted frame and declared closure;
an enclosing orchestrator is not required unless its capability is an actual
prerequisite. Separate Product dependency cycles from current work prerequisites.

A → B and B → C do not grant A access to C. Shared targets keep their separate
route permissions; byte deduplication cannot union them. Adequate provider
contracts can encapsulate internal dependencies, while material far-side reliance
must remain available through an authorized route. Source-owned meaning, receiver
policy eligibility, access/disclosure authority, actual exposure and semantic
adequacy are distinct.

Inspect tool outputs and summaries as information sources. An allowed filename
can still contain forbidden donor information. An owner-approved export must
also satisfy the receiving engagement's eligibility/provenance policy. A
Reviewer may have a separately authorized wider causal-cone view without granting
Worker disclosure. A child gets its own bounded view and grant, not all of the
parent's accumulated context or transitively reachable sources.

Do not declare prior actor knowledge or authored-output provenance complete merely
to satisfy a tool field. Preserve unknown influences and the actual policy
requirements. Ordinary context construction and a strict completeness/clean-room
claim are different obligations; consume the tool's actual boundary and refusal.

On change/recovery, reacquire the exact declaration and affected source/currentness
facts, and distinguish unchanged candidate bytes from unchanged obligations or
evidence applicability. A grant change or prior prohibited exposure cannot be
repaired by deleting a receipt. Hold the affected claim, preserve history and
select fresh eligible work or an explicit owner scope decision. Reuse unaffected
evidence only with its justified applicability.

The current guard operates over mediated cooperative-local acquisitions. It does
not provide OS confinement or certify all actor knowledge. An unrestricted
shell, index, network or inherited-context route prevents a broader clean-room
isolation claim unless separately controlled and assessed. If permitted material
cannot support the decision, return the missing adequacy condition instead of
silently widening access or dropping a required premise.
