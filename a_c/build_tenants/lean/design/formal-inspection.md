# Retained formal evidence inspection

The release consumer needs an owner-provided read-only check of retained evidence before packaging, independently of the required actual cold verification and fresh recheck. `formal_gate.py inspect-evidence --bundle DIR --request CURRENT_REQUEST` is that boundary. The external request selects exact current model/carrier bytes, ordered selections and supplied views; bundle text cannot select a different subject or weaker claim list.

The inspector reuses the gate's parser/importer, closure certificates, proof generators, theorem audit, runtime output mapping, `formal_reuse.bundle` and compatible runtime pin checks. It reads every inventoried member and refuses missing or extra population, missing proof source/object/log, stale runtime/support, altered model/request/views, omitted or arbitrary claims, changed regenerated proof sources, incomplete audit coverage and unsupported axioms. This inspector profile requires the fixed cold execution counts/stages. An authenticated reuse bundle requires a separate `check-evidence --fresh` before this cold-profile inspection. Stored counters and logs are consistency data, not independent process attestation.

Output is `a_c.formal-gate.inspection/1`, status `consistent`, `refused` or `incomplete`, with exact result/manifest/current runtime/model/request/selection/view identities and a declared checks list. `consistent` is retained-evidence consistency/currentness; it is never a new execution or Lean verification verdict. Actual cold execution and required fresh `check-evidence` retain separately bound process transcripts. Static release gates must not turn this inspector's status into a claim of new execution.
