# Deliver a_c for users' own projects

Selection: [T-015](../../tickets/active/T-015-user-project-product.md).
Common outcome: [PU-01–09](../../../specification/requirements/project-use.md).

## Product boundary

STDO defines and organises the user's project as an axiomatic program. a_c
helps make that program explicit, inspectable and usable in construction. The
user's project owns its requirements, algorithms, implementations and evidence.
The same a_c capabilities used to document and check STDO apply to that project.
Graphify and Lean remain realizations of distinct capabilities in the existing
a_c Product. A separate product or another project lifecycle adds no value here.

The immediate target is a public, repeatable workflow. It connects existing
capabilities; it is not a new claim that arbitrary project prose is formally
proved. The 3.0.3 bundled explorer is one documentation application of this
product and currently represents historical common source 35fb4824.

## What exists and what remains

| Capability | Existing realization | Remaining user-delivery work |
|---|---|---|
| Exact model and reversible carrier | Graphify `ac_graph.py`, all eight families and declared acquisition | Bind a user's Product Definition, source and compatible model/profile through a supported front door. |
| Source-to-model authoring | `ac_generate.py` and grounded/repaired authoring paths | Expose the public preparation, authoring, coverage and refresh workflow without study-specific setup. Test an unseen non-STDO source. |
| Reading UI | `ac_explore.py`, standalone full-record 2D/3D reader | Project-neutral defaults, public source-selection guide, installed packaging and refresh integration. `--title` already accepts a project title. |
| Structural/formal checks | Lean reusable gate, exact closure and retained-view proofs, current-proof reuse | Present operation prerequisites and exact checked scope in the user workflow; exercise installed toolchain acquisition and explicit unsupported profiles. |
| Worker/reviewer support | Public FD CLI/MCP, context, preflight, dispatch and evidence operations | Bind the user's actual consumer-method profile and authority. Historical RC9 or 3.0.1 profile support is not automatic support for every 3.0.x cut. |
| Product composition | Existing FC requirements and route/provenance enforcement | Integrate project selection with leaf and parent views; qualify cross-project delivery on an actual composed subject. |
| Distribution | Source checkout, historical applications, bounded Lean source package and new STDO documentation payload | One documented install/use path for the selected capabilities, optional engine prerequisites and independent installed-use qualification. |

Component success and the original STDO case are useful evidence, but do not
yet demonstrate the requested user-product outcome.

## Ordered delivery

1. **Bind the public workflow.** Resolve the selected Product Definition and
   exact method/profile; reuse the existing operation catalogs and artifacts.
   Decide the minimum front door and installer. Record supported contracts and
   refusals before adding conveniences. Do not create a duplicate project store.
2. **Deliver one leaf end to end.** Use the invoice-export subject in PU-09.
   Carry source → proposal → documentation/checks → selected context → source
   refresh through public interfaces. Reuse the existing engines and evidence
   forms. A user must not edit tenant source to introduce their own project.
3. **Carry the result into actual work.** Run the selected Worker and independent
   Reviewer on the same exact project cut, preserving their distinct source
   access and actual received context. Test stale evidence, missing retained
   constraints and inadequate budgets. Separate generated implementation tests
   from structural proof and interpretation assessment.
4. **Compose independently owned leaves.** Add the provider and parent to the
   same exercise. Show permitted contract acquisition and prohibited internal
   acquisition, including retained inline context. Check recursive views and
   shared-provider identity without unioning grants or flattening authority.
5. **Package and independently qualify.** Install outside the development
   checkout; use the documented commands and exported reader. Assess complete
   user outcome and measured cost. Record remaining limits, then make the a_c
   acceptance/distribution decision and any selected STDO bundle update.

Close each increment on its concrete outcome and unresolved obligations. Do
not keep recataloguing the engines, add a generic agent framework, or expand
the Lean fragment before the selected user exercise demonstrates the need.

## Release relationship

STDO 3.0.3 documentation integration can finish independently of this wider
user workflow. The current task does not make the entire new product a 3.0.3
release prerequisite. If the reusable tool package is selected for a later
STDO distribution, its exact package and supported profiles must be explicitly
bound there; documentation inclusion alone is not tool installation. Each
product keeps its own acceptance and release decision.
