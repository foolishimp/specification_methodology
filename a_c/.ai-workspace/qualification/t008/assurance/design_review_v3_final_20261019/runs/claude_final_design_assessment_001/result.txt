## 3. Source-bound findings

### Finding 1 — Notification sink binding is required but has no lawful home in the closed policy schema

**Locators (`fd-support.md`):**
- Line 392–395: policy closed top-level keys, which include `event_sinks`.
- Line 451: Grant exact fields: `id, authority_sources, outcome, principals, targets, operations, tools, executors, territory, preconditions, admission`.
- Line 453: Executor exact fields, which also contain no notification field.
- Line 441–443: "Registry populations are id-keyed objects; duplicate ids/unknown fields refuse."
- Line 792: the Attempt payload has `notification`.
- Line 1446: the reservation encloses the "notification sink".
- Line 1536–1539: "Grant/executor notification binding chooses only a registered id … public requests cannot register an endpoint."
- `dispatch.start` arguments (line 243) carry no sink selection.

**Entry and causal path.** An operator authors a policy for FD-007 notifications.
- Any field placed on a Grant or Executor to name a sink is refused as an unknown field.
- No request argument can select a sink.
- The Attempt's `notification` value therefore has no policy-sourced derivation.
- An implementation Worker must choose between at least three readings: a new Grant field, a new Executor field, or a single implicit sink. These differ in who selects the declared consumer of delivery, which is authority-relevant (EXEC §6 Event-driven attention; F4 sink rows).

**Affected actors and relations:**
- The Effect Worker and Integration Worker, who hold the disjoint grants (lines 1238–1249).
- FD-007 notifications, SC-AC-FD-014, and the Attempt reservation enclosing relation (F2, line 1446).

**Material consequence.** Implementation would establish a material public-contract and authority choice that the design was required to settle. This is exactly the DESIGN_MODULE §5 "implementation has to introduce a new material semantic decision" condition.

**Uncertainty.** An implementer might read lines 1536–1537 as implicitly extending the Grant/Executor schema. That reading still contradicts the "exact fields" tables. Either way the network is not unique.

### Finding 2 — "Explicitly registered external producer" for returns has no registry

**Locators.**
- Line 247: `return.capture` output "must be from that attempt or an explicitly registered external producer, otherwise unauthenticated."
- Line 392–395: the closed policy keys contain no producer registry.
- Line 449–451: the Principal registry is for startup requesters, not return producers.
- Lines 617–626: conjunction cardinality depends on an "authenticated closed evaluation".

**Path.** A Reviewer or assessor run that was not launched through `dispatch.start` cannot be authenticated. This applies, for example, to the Claude CLI assessment that the plan says Executive "separately activates" (line 1224–1225).
- A lawful fallback exists: such a return is treated as unauthenticated and therefore a planned-assessment gap.
- The named "registered external producer" branch is nonetheless undecidable.

**Affected relations.** FD-008, FD-010, and the independence/assessment cardinality seam.

**Consequence.** Either the branch is dead text, or implementation invents a registry and its trust semantics. This is a secondary underconstraint. On its own it might be closed by declaring the branch unsupported.

### Finding 3 — Cross-module export lists diverge between the module table and the realization seam

**Locators.**
- Module table, lines 718–720:
  - core exports `execute_read` and `build_preflight`, with no `prepare_write` or `make_artifact`;
  - effects exports `dispatch, supervise, observe_attempt, cancel, wait_events, write_record, retain_operation`.
- Realization seam, lines 1744–1779:
  - core also exports `prepare_write -> EffectPlan` and `make_artifact`;
  - effects exports `execute_effect` and `persist_outcome(runtime,request,outcome)`;
  - `EvidenceStore.resolve/query_artifacts/retain` (lines 861–866) are also listed.

**What the seam says.** "Full-request handler signatures … remain normative." The seam supersedes the CoreOutcome draft, but it does not state whether `retain_operation(runtime,request,response)` and `persist_outcome` are the same function. It also does not state who constructs the Writer EffectPlan: core `prepare_write` or effects `write_record`.

**Affected actors.** Workers 1 and 2 develop disjoint modules "against these accepted contracts" in parallel, and Worker 3 integrates.

**Uncertainty.** These may be compatible supersets. Equivalent local helper names are allowed, but these are declared cross-module seams.

**Consequence.** There is a risk of an integration mismatch that a seam-defect re-entry would then have to resolve. This is ambiguity, not a demonstrated contradiction.

**Uncertainty.** Part of this may be ordinary schema realization delegated to the core Worker (line 736). However, the semantics of an invalidator and a counter identity are not purely layout.

### Finding 5 — Contract-state population omits `superseded`

**Locators.** ACTIVATION §1 Admission requires that contracts carry at minimum drafted, admitted, rejected and superseded states. The receipt-validity view (lines 1584–1599) and the lifecycle row (line 1513) use Draft, Rejected, Admitted, Applicable and StaleForUse. Supersession appears only as "separate finding/receipt". The `preflight` payload `decision` enum is not enumerated (line 791).

**Consequence.** The FD-006 representation of a method-owned state is incomplete. The material scope is narrow: admitted-then-superseded contracts are distinguishable only through prose.

### Finding 6 — Wire mapping of held outcomes to status and exit code is underdetermined

**Locators.**
- Lines 187–194 define status `ok|refused|error`, CLI exit codes 0/2/1, and "error preserves caught external failure and unknown effects".
- Lines 1344–1352 put `held(observation)` and `held(effect)` codes (`internal_failure`, `effect_completion_unknown`) in the "refusal `code` population".
- It is not stated whether a held outcome carries `status: error` with a refusal object, `status: refused`, or `status: ok` with a truthful unknown receipt. Lines 1372 and 1817 suggest the last of these is sometimes possible.

**Consequence.** Ordinary CLI callers could see different exit codes across implementations for the same operation outcome. This has minor contract-sufficiency impact. The `operation_outcome` value itself is unambiguous.
