## Material Changes

### ODD_METHOD §11.5D Constructive Evaluation And Yield Loop

`ODD_METHOD.md` now ratifies the constructive evaluation and yield loop as
constitutional law for any ODD product over GTL/ABG.

The loop carries authority shape:

```text
IntentLineage
-> ProductAssetModel
-> ObservationSnapshot
-> GapPressureRow
-> TargetObligationBinding
-> PriorityProjection
-> ConstructionIntent
-> AdmittedEvidence
-> EdgeFulfillmentLedger
-> EdgeClosureDecision
-> NextActionProjection
```

The loop names four distinct evaluation functions:

- `synthesize_model` — synthesizes the product asset model from intent lineage,
  prior model, and admitted product truth
- `eval_gap` — emits observation snapshot and gap pressure rows from the model
  against runtime and worksite truth
- `evaluate_next` — selects the next lawful published graph action from gap,
  binding, catalog, and policy
- `evaluate_action` — folds admitted evidence into the edge fulfillment ledger
  and closure decision

The word `evaluator` alone is no longer sufficient. A design, ticket, code
module, or proof must name which function it implements or consumes.

The loop is governed by axioms A0 through A16, including:

- A0 One Surface
- A4 Evaluate_Next Totality and A4a Evaluation Function Separation
- A8 Closure Decision Is A Sum Type with vocabulary
  `{close, yield, retry, repair, re-enter, reprice, block}`
- A9 Yield Is Lawful Iterate
- A11 Re-Entry Is Graph Law
- A13 Replayability and A13a Causal Chain Integrity
- A14 Recursive Published Refinement
- A15 Method Ownership
- A16 Constitutional Override, naming the rival-artifact list and precedence
  rule

The constitutional equation explicitly threads `synthesize_model`, `eval_gap`,
`evaluate_next`, and `evaluate_action` through the post-action loop refresh,
including `NextActionBasis` dispatch.

### SPEC_METHOD ADR Governance

`SPEC_METHOD.md` ADR Conventions now require:

- `Status:` with values `active`, `superseded`, or `retired`
- `Superseded by:` when an ADR is in `superseded` state

A new `ADR Folder Convention` section ratifies:

- tenant-local ADRs at `build_tenants/<tenant-path>/design/adrs/`
- cross-tenant ADRs at `build_tenants/common/design/adrs/`
- non-tenanted ADRs at `<governing-design-surface>/adrs/`

The `<tenant-path>` generalization makes both `<family>/<variant>` and
single-label tenant paths lawful, provided the project's
`build_tenants/TENANT_REGISTRY.md` records the tenant identity used.

### Build-Tenant ADR Templates

Four constitutional templates publish the ADR convention:

- `common/design/adrs/README_TEMPLATE.md` — when to write a cross-tenant ADR,
  file shape, frontmatter requirements, supersession rule, optional registry
- `common/design/adrs/ADR_TEMPLATE.md` — canonical body shape with
  Context / Decision / Consequences / Alternatives / Notes sections
- `variant/design/adrs/README_TEMPLATE.md` — tenant-local ADR conventions
- `variant/design/adrs/ADR_TEMPLATE.md` — tenant-local ADR body shape

### Template Path Generalizations

Tenant references across templates now use `<tenant-path>` rather than
`<tenant>` or `<techlabel>`:

- `EDGE_OVERRIDE_TEMPLATE.json` `design_refs` use `<tenant-path>`
- `TENANT_REGISTRY_TEMPLATE.md` records that single-label tenant paths remain
  lawful per `SPEC_METHOD.md` `## ADR Folder Convention`
- `common/design/README_TEMPLATE.md` and `variant/design/README_TEMPLATE.md`
  declare an `adrs/` subsurface alongside the existing design surfaces
