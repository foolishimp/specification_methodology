## Position

`v1.8.0` ratifies the operational lifecycle sufficiency cut.

The release strengthens the shared method so products, applications, modules,
graph functions, build tenants, runtime surfaces, and other designed surfaces
are treated as implementations of constitutional documents, not substitutes for
them.

The release also single-sources the operational lifecycle chain in
`SPEC_METHOD.md` and requires `DESIGN_MODULE_METHOD.md` to confirm that chain
at realization boundaries before design-method closure.

## Material Changes

### SPEC_METHOD Operational Lifecycle Sufficiency

`SPEC_METHOD.md` now defines the canonical operational lifecycle chain:

```text
intent
  -> requirement
  -> build
  -> assurance
  -> release
  -> deployment
  -> live usage
  -> observed telemetry
  -> retirement
```

Product and requirement surfaces must now provide enough lifecycle signal for
downstream design, or record a named ambiguity gap. This signal is
materiality-scoped: the method does not require every requirement to become a
release plan, but it does forbid silent absence where release, deployment,
live usage, telemetry, or retirement materially affect the product or
obligation.

The new rule makes explicit that downstream design may not fill missing
lifecycle truth from implementation precedent, prompt prose, local convention,
or test-only fixtures.

### DESIGN_MODULE_METHOD Lifecycle Confirmation

`DESIGN_MODULE_METHOD.md` now includes the Module Lifecycle Confirmation Rule.

Every governed module, function, application surface, runtime surface, plugin
surface, public interface, data surface, graph function, or GTL module must
confirm the canonical lifecycle chain before claiming design-method closure.

Each lifecycle phase must be:

- answered by the active design, requirement, release, deployment, or telemetry
  surface
- declared not applicable with a reason
- recorded as a named `Gap:` or `Unanswered:` item with an owning follow-up

A phase list without answers, not-applicable reasons, or named gaps is not
design-method evidence.

`DESIGN_MODULE_METHOD.md` explicitly does not replace `RELEASE_METHOD.md`.
Release eligibility, tap acceptance, install policy, and operational rollout
remain governed by release and project-owned operational surfaces.
