## The observation

The delivery ran eight steps under STDO 3.0.0 with a Fable Executive, Opus
Workers and Fable Reviewers. Its churn had one shape. Nearly every stop,
repair and wrong ruling was a named check nobody ran:

- the import graph behind a layering claim (a Worker stopped; D6);
- the stored digests over derived state behind a new fluent (a Worker
  stopped; D7);
- the old-instance reading of a stored artifact that gained a member (D8);
- the sibling throw sites beside the two an activation named (a review
  finding and a repair round);
- ten edited test suites outside the run list (a whole-diff finding);
- three repairs that closed a local condition and dropped part of the
  obligation (a thrown error in a child process accepted as "facts reach
  the log"; a batched copy accepted as "the fold is linear"; recorded type
  debt accepted as a discharged obligation).

The two wrong Executive rulings (a replay-witness trace; a lifecycle guard)
were made by the strongest model in the allocation and corrected by review.
Census-style Worker activations (a 47-occurrence classification; an AST
census; a baseline attribution over 44 suites) ran their named checks
reliably with the cheaper model.

## The principle

Expertise is paid for once, in the decomposition, and cached as process
structure that cheaper execution carries: trace tables, obligation lists,
census activations, run lists, completion conditions. Execution cost then
scales with the volume of checks, not with the intelligence needed to find
them. A failure of execution is answered by naming the missing check and
adding it to the structure, not by a smarter executor. The smart agent's
remaining work is the unnamed class (review) and the decomposition itself
(Executive), and an Executive ruling is a claim a Worker verifies against
the code and the design text before it applies.

## What 3.0.1 could carry

For triage against the 3.0.0 role model and the activation/return
contracts, not as wording:

1. Activation structure: a design-step activation carries trace obligations
   as a table in the Return (structure claims to code sites; persistence
   changes to their old-instance reading; derived-state changes to the
   digests over them; every proof names an existing check; every edited
   test in the run list).
2. Rulings: an Executive mid-step ruling is a claim; a Worker verifies it
   against code and design text before it applies; a refutation by the
   design's own text reverses the ruling rather than restating it.
3. Repairs: a repair Return is verified against the obligation's full path,
   not the local site the finding named.
4. Allocation: the Reviewer slot carries the strongest model, including on
   the design step; Workers carry the structure; the structure, once
   written, is reused across deliveries as cached expertise.
5. Cost record: a ledger notes which failures were named-check misses and
   which were unnamed classes, so the structure grows from evidence.
