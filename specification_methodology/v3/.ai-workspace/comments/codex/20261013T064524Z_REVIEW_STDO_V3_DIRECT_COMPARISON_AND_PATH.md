## 2. Architectural comparison

### Different ownership strategies

Codex adds an explanatory premise layer and a conditional contract library while retaining the predecessor's deciding owners. F1–F6 are adopted domain commitments, explicitly distinguished from consequences and independently chosen policy. Bind, Acquire, Transform, Evaluate, Conjoin and Dispose are responsibilities that can share an invocation, not six compulsory stages. Particular methods retain concrete types, result algebras, admission and grants (K:FOUNDATIONS.md:48–80,265–284; TRANSFORMATION_LIBRARY.md:3–25,59–112).

The work/recovery table is its strongest foundational chain. It names premises, consequences, source owners and independent choices. Its deciding consumer is the ordinary work entry, which routes interrupted work to the work/recovery view and other tasks to their view or deciding owners. Three views embed library clauses; domain-binding and release/adoption rely on the particular owners (K:TRANSFORMATION_LIBRARY.md:93–118; Codex `successor/plugins/spec/skills/stdo-work/SKILL.md:18–39`; KQ:FRAME_INPUTS.json, `frames[*].routes`). This is actual partial integration. It does not account for every remaining family to the same depth. The current return explicitly leaves whole-corpus foundation reconstruction and member acceptance open (KQ:RETURN.md:12–25).

Claude instead moves ontology and shared operation into a generic core. FOUNDATIONS owns the objects and commitments, ACTIVATION owns admission/context/results/refinement/recovery, REFERENCE_FRAME states the frame laws, and EVALUATION owns claims, independent assessment and acceptance. Particular methods consume these owners, and profiles declare their bindings (C:FOUNDATIONS.md:3–5,40–59,292–367; ACTIVATION.md:3–18; PROFILES.md:3–24).

The inspected consumers make this more than a new naming scheme. SPEC_METHOD consumes the foundational Outcome and EVALUATION acceptance relation; TICKETS consumes ACTIVATION admission; ODD explicitly binds its cumulative environment to generic refinement; DESIGN_MODULE consumes the shared-machinery distinction and preserves separate semantic and realization dispositions (C:SPEC_METHOD.md:550–586; TICKETS.md:536–557; ODD.md:258–280,1318–1346; DESIGN_MODULE.md:1393–1431).

This is a stronger integrated proposal in those cones. It also introduces generic policies and translations that need qualification. Default cross-family independence and the profile vocabulary boundary are policy choices, not consequences of finite resources (C:EVALUATION.md:101–104; PROFILES.md:9–28). Merely attaching P0–P6 does not complete a derivation for every member.

### A shared standalone dependency

Both editions define `AxiomaticCalculusBasis.derivation_basis` using predecessor-cut clauses. More decisively, both Traversal profile admission procedures require the predecessor manifest, exact predecessor member bytes and resolving fragments; an unbound predecessor byte sequence refuses admission (K:AXIOMATIC_CALCULUS.md:905–916; TRAVERSAL_OCCURRENCE_PROFILE.md:1189–1207; C:AXIOMATIC_CALCULUS.md:993–1005; TRAVERSAL_OCCURRENCE.md:1302–1324).

This is not only the lawful choice to use installed rc.2 mechanics while constructing v3. It is a deciding procedure for a successor profile basis. Removing predecessor access prevents that procedure from completing. A "provenance" label or absence of a hard-coded rc.2 URI does not remove the dependency.

The fix is shared release/identity policy: retain authentic derivation coordinates and the separation between content identity, judgments and publication, while defining how successor issuance/admission has all evidence it needs in the successor's admitted package or exact, accepted verification relation. Merely deleting the historical coordinates would weaken a conserved identity determination. The concrete remedy needs the identity/calculus/profile and packaging owners, and a named successor disposition. Neither candidate settles it.
