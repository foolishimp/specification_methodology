## Findings

### B-01 — P2: Functional preference is turned into an absolute rule, contradicting an express permitted case

**Exact candidate:** `DESIGN_MODULE.md:396–401`, against `378–386`, `134–142` and `1787–1795`.

The functional-bias list prefers immutable carriers over mutable shared objects. Lines 396–401 then say any realisation that forgoes a preferred shape does not conform, with no exception except the one failure-carrier item saying “where practical.” The same member's immutable-carrier owner expressly permits mutation when materially necessary, with explicit justification for a performance-critical case, host/runtime/framework requirement, or genuinely stateful boundary. The earlier invariant also requires minimizing and justifying shared mutation rather than categorically forbidding it.

**Independent counterexample:** an adopted design profile runs in a host whose interface requires a mutable carrier. The design has considered the immutable alternative, shown why it cannot satisfy the host contract, confined mutation to admitted transitions, and retained explicit effects and authority. Section 10's express host-required case permits this design; section 4's added absolute sentence rejects it solely for forgoing the preferred carrier.

**Violated obligation:** common `requirements/README.md:32–34` requires conservation of source meaning, including qualifications and exceptions; line 66 treats preference strength distinctly from an unconditional implementation mandate. The single-owner obligations at `133–153` also disallow rival deciding rules inside consumers. Mandatory preference is a duty to prefer and justify; it does not erase the source's stated necessity exception.

**Predecessor confirmation:** installed v2.5.1-rc.2 `standards/DESIGN_MODULE_METHOD.md:255–277` carries “must prefer” and “must avoid.” Its `1863–1878` separately retains immutable values unless mutation is materially necessary and expressly includes host/runtime/framework requirements. The candidate's assertion that the predecessor admits no such exception is therefore wrong, rather than a merely debatable interpretation of “prefer.”

**Impact and smallest owner fix:** lawful implementations can be denied conformance, and two readers using the same member reach opposing judgments. Revise the blanket nonconformance sentence so the preference remains binding while preserving the explicitly owned material-necessity exception. Refer to the immutable-carrier owner rather than restating an incompatible exception set. Actual prohibitions in the avoid list need not be weakened.

### B-02 — P2: Material no-action determinations are excluded from the one result system

**Exact candidate:** `ODD.md:985–988`, `990–1025`, especially `1019–1025`; corroborating family characterization at line 130. Shared owners: `FOUNDATIONS.md:112`, `792–816`; `ACTIVATION.md:945–959`, `1016–1034`.

`evaluate_next` decides from the current gap, binding, catalogue and policy. Its published-action law returns a typed no-action disposition when the required action is unpublished. Other branches decide authority absence, block, or unresolved constitutional re-entry. The member nevertheless says selection, “a typed no-action disposition included,” maps to no core value; only a preceding closure, “where there is one,” supplies a result.

**Independent counterexample:** lawful `initial_selection` has an admitted Product outcome, a fresh gap requiring action X and an exact catalogue that does not publish X. There is no prior action or closure. A3 itself makes the public determination that X cannot lawfully be selected and returns typed no-action. A4 excludes that disposition from the result algebra. The evaluator may have successfully produced a `NextActionProjection`, so construction availability can be `candidate_ready`; that result proves output availability only. No later action admission occurs for X and therefore cannot supply the missing predicate/result for the determination already made.

**Violated obligation:** common `PRODUCT.md:127–138` and `requirements/README.md:155–176` require material evaluation and authorized decision outcomes to remain in the singular result system. Line 174 carefully exempts an ordinary selected action or classification from automatically being an evaluation, but says the exemption does not remove material compliance, admission, closure or disposition determinations. The candidate's own definition includes action recommendation within evaluation; its core requires each performed evaluation's predicate, domain outcome and core result.

This finding does **not** require every selected action ID or internal ranking computation to become a method result. It concerns the public material lawfulness/authority determination that produces the no-action disposition. Nor does it dictate one core value for every no-action case: a declared predicate is needed before a mapping can be assessed. “No lawful action exists” and “an action is available” are different predicates.

**Impact and smallest owner fix:** a consumer combining the evaluator's work with other results cannot distinguish output availability from the actual lawfulness determination through the required common algebra. A preceding closure cannot repair initial selection, and would concern a different predicate in any event. Keep selected-action payload data separate, but name the predicates and core mappings for the material no-action and authority determinations, preserving their causes. Reconcile A4 and the family table with the generic step-result contract; do not turn later admission into a duplicate or substitute assessment.
