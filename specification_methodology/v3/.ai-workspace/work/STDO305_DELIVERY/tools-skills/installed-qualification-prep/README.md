# Installed qualification preparation

These operator scripts and prompts prepare the already authorized finite qualification cases. They are not Product runtime source or a qualification verdict. Run them only against the actual selected nativeA installation, a verified writable runtime derivation after bootstrap, and the corresponding installed Skills CONFIG. Keep accepted source candidate008 fixed.

`prepare_native_inputs.py` takes explicit installed configuration, current model, views, formal request, current installed proof bundle and checker selection. It verifies the installed runtime through its actual `check-runtime` command and runs the public read-only initializer. It then creates a fresh, separately scoped project and controlled grant policies under an absent output directory. Each policy binds the real installed method; no synthetic native cut or global host configuration is created. The Product-local grant is an operator realization of Root's existing qualification setup/effect instruction, not authority inferred from installation.

The prepared cases are missing issuer grant, missing recipient grant, unreconciled prior effect, and one formal current-model Context. Preparation does not dispatch a process or invoke Lean. `record_public_call.py` records actual public support calls from these fixed policies, without a shell or policy override. The uncertain case must first receive one actual controlled process attempt; retain its observed evidence and supply the retry request to the host. Do not replace that activation or erase history.

Each case has distinct Product, policy, activation, authority record and evidence identities derived from its explicit output root. The missing issuer removes the actual dispatch operation; the missing recipient removes the actual grant target. The final review has its own Product and Reviewer intake after the Worker cases. Its complete return preserves technical severity separately from Executive priority and disposition. These are separate declared activations in one CLI process, not an assertion of enforced context isolation or a clean room.

For the current Context case, acquire its actual public context. Compare its ordered view with the selected native-work 21-record view before preflight. Preflight is a new current, context-bound proof and requires Root's serialized heavy slot. Retain the actual formal bundle, inspect it under the selected runtime, then dispatch the controlled recipient and compare its complete received stdin and view bytes. A fresh source request with an omitted required record already has a retained real kernel refusal in current-formal-005; the installed delivery control additionally checks that an altered/omitted delivered view cannot consume the existing proof. Use a separate, explicitly adversarial evidence artifact if testing a rebound context; never edit the original cold proof or immutable installation. Stale-proof checks operate on a private independent copy or a separately retained modified report, with no hardlinks.

The host prompt template names four required behaviors. Run a fresh Codex session and fresh Claude session only after their packages and all selected inputs are verified. Use requested effort xhigh where supported, exact CLI argv, explicit selected model, a disposable target directory, and session-local settings. Authentication may use the existing host path without reading or recording credentials. No user/global settings, personal browser profile, project Git state or released installation is mutated. Record requested and observed model separately; unresolved model identity is reported as unknown. Source-first review is bounded to the controlled candidate and does not imply cross-family review.

The final reader/browser run uses the installed offline files with the already authorized fresh headless profile, no network requests and no unrelated file navigation. Source and proof relative links must resolve from the installed file origin. Construction viewer checks do not replace that run.
