# Tools and Skills delivery design for STDO 3.0.5

Status: Executive accepted this design and the exact native-profile initialization boundary before implementation. The full installed inventory is rechecked on every public operation; no persistent positive cache is introduced.

## Outcome and ownership

The owner-selected five-Product cohort has version 3.0.5. This Writer owns a_c and STDO Skills, including their public reader, formal-gate and host interfaces. The release Writer owns native core skills and release assembly. Generic viewers and Lean remain a_c build-tenant capabilities, never new Product identities. Construction adopts released STDO 3.0.4, manifest `102817a3f4bea4dca1d6fa0fc634b94404dd2ba82ba6d8c38b273402dda9f95b`; previous builders and trial evidence retain their original identities.

## Immutable target binding without a manifest cycle

The construction sequence is frozen normative source S, generated complete payload, native cut A, then external cohort binding B. The 3.0.5 a_c method profile records exact S owner member digests and explicit preserved/changed contract mappings. It records the target release URI, but cannot embed A's future manifest digest in source that A itself includes.

The proposed trusted startup policy adds `method_installation`: a registered read-only installation root. At startup the tool reads the actual installed manifest, requires its digest to equal the exact consumer Product basis, requires the 3.0.5 cut, verifies installed member bytes, and checks every normative owner against the frozen profile. The request envelope cannot supply or replace this trusted policy coordinate. The ordinary manager's `status --verify` is also retained by setup. An external final B binding can be selected by setup and checked against the same installed A. No arbitrary profile, caller-provided success label, mutable source or selector is accepted as exact target support.

The 3.0.1 and RC9 profiles remain available with their original identity and result mappings. Native `results.conjoin` remains an honest unsupported operation unless separately implemented and qualified. Source-level contract comparison determines actual semantic preservation; equal wire shape is insufficient.

## Skills and installation

The common native `stdo-work`, `stdo-review`, `stdo-ticket`, `stdo-status` and `stdo-help` skills remain the workflow owner. STDO Skills 3.0.5 supplies independently designed Codex and Claude host bindings plus one named extension per host for project representation, formal reading and code overlays. A coherent installation includes the exact core package and its selected host extension; it must not install a second `stdo-work` or silently enable the other host.

A Product-local Python installer verifies source inventory, contained regular files and absent destination, installs the selected host bundle with a receipt, and supports verified update/removal without touching unrelated host settings. The package carries resolvable relative resources. The a_c package supplies usable CLI entrypoints plus an explicit isolated runtime bootstrap. Source archives alone are not installation completion.

## Runtime prerequisites

Base tools and offline reader: Python 3.12-compatible standard library and a browser supporting Canvas; WebGL enables 3D, with 2D and Layered available independently. Nominated project preparation also needs the selected STDO manager and verified target installation. Optional Graphify uses exact commit `fe085cedddde3a18554f8749b230bfe47f3dcce7`, version 0.9.90, and the pinned Python dependencies already declared by the tenant. It is not needed for direct authoring.

Formal verification uses the existing private toolchain bootstrap, Lean 4.35.0 commit `eb6cafb7290e8bd5f2937522d8d804f58f02bafc`, Mathlib commit `56a005855ea17e0b0958f73ec801ae140b0a1679` and pinned transitive Lake manifest. Its bootstrap needs curl, Git, tar/zstd and network access to exact upstream archives/caches; no global toolchain is mutated. Compiled proof support is platform-specific and requires explicit local establishment. Historical compiler bounds do not cap observed RSS; Executive serializes heavy full-model runs.

## Preserved history

Historical dogfood, applications and proof receipts are immutable evidence inputs for this work. Current documents explicitly supersede only current routing/status. No old proof or host trial is renamed as 3.0.5. No commit, tag, push or peer-territory write is performed by this Writer.

## Runtime installation and nominated Product basis

The Skills installation configuration binds a 3.0.5 runtime anchor Product only to verify the installed native package. It grants no adoption or basis rewrite. Each operation resolves the nominated Product Definition independently. Generic project/code operations retain that Product's exact selected basis; the native305 FD initializer requires that nominated Product to select the supported exact 3.0.5 cut and refuses an old-basis selection. Installation, plan, verification and removal do not invoke adoption. Tests retain the nominated definition bytes across a supported generic project build and across a refused native305 installation/setup.

## Materialized runtime boundary for review

The verified immutable method root remains read-only. Bootstrap is a separately authorized effect in a writable a_c materialization: it owns private Graphify/Lean dependencies and fresh local proof-support establishment, retaining prior support bytes. It is not an operation against the immutable native method install. Host provider pins must be selected after bootstrap and fail currentness after later runtime source/profile changes. Review must assess this distinction without treating either runtime installation or a caller-supplied target as Product adoption.

## Independent review repair and additional owner adapters

Repair disposition preserves POSIX virtualenv invocation spelling and records physical executable identity separately. Both host routes must invoke the selected environment after actual installed runtime checking. The method boundary rejects resolved overlap of evidence/result storage and effective writable source scopes before EvidenceStore construction, while retaining disjoint writable scopes.

The formal owner supplies the read-only inspector described in `a_c/build_tenants/lean/design/formal-inspection.md`; actual proof execution remains separate. The Graphify owner supplies an installed roundtrip command over a selected model, carrier and ordered selections, reusing existing codec and exact upstream build/export/load behavior. It retains graph/view/runtime/source/module pins and observed Python prefix rather than reporting generic success or CLI help. These adapters add observability of existing semantics, not new method law. Source S remains unchanged.
