**Part 1: Lawfulness of identity use (facts 1 to 4)**

1. **Unlawful.** The engine would be imposing a domain grammar on domain-owned objects, and it would be silently inventing meaning.
   - The current identity is authority `field-notes` domain (and the owning lab scope), kind `requirement`, value `REQ-7`.
   - The proposed `runloop:req:<uuid>` puts the engine in the authority position for a requirement. That changes the authority coordinate.
   - Parsing the digits of `REQ-7` into a priority field gives the value a semantic reading that the domain never defined. The domain defines how its ids are parsed or read.
   - The old id is replaced with no explicit relation between old and new. This breaks the stability clause.
   - A lawful alternative is for the engine to transport `REQ-7` unchanged. A domain-defined mapping, with the old-to-new relation made explicit, could also be used.

2. **Unlawful.** The scope coordinate is collapsed.
   - The two identities are (`lab-a`, requirement, `REQ-7`) and (`lab-b`, requirement, `REQ-7`). Both are live, they are the same kind, and they sit in different authority scopes.
   - Each is lawful inside its own scope. The flat file keyed only by `REQ-7` drops the authority coordinate. That creates an accidental collision and makes the two indistinguishable.
   - The serialisation must keep the hierarchy, for example by including the lab scope in the key. Any aliasing across scopes must be explicit.

3. **Unlawful.** Kinds are collapsed in two ways.
   - `REQ-F2` is a requirement_family identity (authority `field-notes`, kind `requirement_family`, value `REQ-F2`). The report treats it as a concrete requirement ("requirement REQ-F2 satisfied"). The method does not treat a family identity as a concrete requirement identity.
   - `2.1.0` is a release version. It is used as the identity of the dashboard object. A release version is not object identity.
   - The dashboard object needs its own scoped identity. The kind that applies is not given in the facts. The release can be identified separately as kind `release`, value `2.1.0`.
   - The report also leaves out the authority and scope for both identities.

4. **Unlawful.** The relation between the old and new objects is missing.
   - The identities are (`field-notes`, requirement, `REQ-9`) for the retired object and (`field-notes`, requirement, `REQ-9`) for the new one.
   - The same authority, kind and value now name two different objects. Identity was silently reused for a different object.
   - The id must not be reused. If the new requirement needs a link to the old one, the relation (supersession or retirement) must be explicit. Otherwise a new value should be issued.
   - The scope is not given in the facts. If it is a lab scope, that coordinate is also unstated.

**Part 2: Ownership**

- **Run ids** (`r-8f3a2c`): the engine `runloop` owns them. Runs are runtime-owned objects. `runloop` may generate opaque ids with its own rules, optimised for uniqueness, replay safety and event-stream integrity. The domain may carry and reference them. It may not impose a semantic grammar on them, and it should not reinterpret them.
- **Event ids** (`e-000193`): the engine `runloop` owns them, on the same basis as run ids. The counter-based generation is lawful. The domain may transport and reference them. It should not invent meaning from the counter.
- **Requirement ids** (`REQ-7`): the `field-notes` domain owns them (scoped per lab). The domain defines the kinds, what makes each unique, and how each is parsed. The engine may transport them. It must not replace them, mint substitutes, or read meaning into them silently.
- **Acceptance criterion ids** (`AC-7.1`): the `field-notes` domain owns them, with the same rights and limits as requirement ids. The domain also owns the meaning of the `7.1` structure. The engine may carry them without parsing the structure. Any link to `REQ-7` is a domain relation, and the engine must not infer it.
