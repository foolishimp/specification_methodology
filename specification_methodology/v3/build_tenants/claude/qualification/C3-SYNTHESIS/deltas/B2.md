### Rows whose disposition changes: parent and child rows

Ruling applied (Executive, on RBb m5): where the successor text changes a
claim's meaning because of the common single result algebra requirement,
the claim is `superseded`, and the replacement relation is item 3 of that
requirement. Each of the five rc.2 sections below has separable parts: one
sentence or clause whose meaning changes, and a remainder whose meaning the
successor text keeps. Each row is therefore split (RBb m4) into a parent
row, `conserved`, and a child row, `superseded`, inserted directly after
the parent. The form is that of frontier lines 651 and 652. A child's
anchor is synthetic, and its bytes are the UTF-8 length of the quoted
rc.2 text.

Why the meaning changes, row by row. In each case the rc.2 text is a
pairing or a mapping from the accompanying core result to the variant.
rc.2 line 480 pairs `incomplete` with `indeterminate`, and line 1322 maps
`indeterminate -> incomplete`. Item 3 replaces that pairing, and ACTIVATION
§3 Construction availability chooses `falsified` for `incomplete`, a value
item 3 does not entail. `refused` and `incomplete` then share `falsified`,
so no core result selects a single variant any more.

- 516: rc.2 says "They are disjoint by their accompanying Reference Frame
  Method result" and "`incomplete` accompanies `indeterminate`". Both
  statements are false of the successor. The other three pairings, the
  grounds, totality, exclusivity, the refusal exclusion and C/J/O reuse
  keep their meaning.
- 522: rc.2 says "one Reference Frame Method result plus exactly one
  `candidate_ready`, `refused`, `incomplete`, or `re_entry_requested`
  profile work-result variant". Read with `#work-result`, an `incomplete`
  Worker returned `indeterminate` there. The successor result is
  `falsified` for "a candidate is available", and each performed evaluation
  keeps its own result. The meaning changes, so B2's reading that the row
  "follows row 516" while staying `conserved` is withdrawn. The other ten
  frame elements and the three paragraphs keep their meaning.
- 543: rc.2 says "Each variant accompanies exactly one Reference Frame
  Method result under the mapping in `Work result`: `satisfied ->
  candidate_ready`, `falsified -> refused`, `indeterminate -> incomplete`,
  and `out_of_frame | invalid_basis -> re_entry_requested`." The successor
  maps the other way, from value to core value. The notation, the
  after-activation condition, the Reviewer exclusion and the stop rule keep
  their meaning.
- 560: rc.2 obligation 5 says "every Worker work-result variant is
  disjointly mapped from its Reference Frame Method result". This holds only
  while each core result selects one variant, which is no longer so. The
  other twenty-five obligations and obligation 5's return to the consumer
  keep their meaning.
- 565: rc.2 condition 4 says "every Worker result maps exclusively from one
  closed Reference Frame Method result". This fails for the same reason.
  The other twenty-three conditions, and condition 4's refusal distinction
  and return, keep their meaning.
