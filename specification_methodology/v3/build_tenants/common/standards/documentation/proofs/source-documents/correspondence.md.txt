## Trusted installation boundary

A 3.0.5-rc.1 trusted policy additionally contains:

```json
{"method_installation": {"root": "installed-method"}}
```

That name selects a registered read-only local source root. Its read scope must
include `manifest.json`, `standards`, `plugins`, `release` and `LICENSE`. At
startup and every public operation, including a long-lived MCP server, the
runtime reacquires the exact selected Product Definition and profile, checks
that the manifest SHA-256 equals the Product's immutable 3.0.5-rc.1 basis, verifies
the entire installed file population and each member digest, then compares all
53 frozen standards and 15 native contracts with the supported profile. No
persistent positive cache is introduced. Before creating an evidence store, startup also rejects overlap between the immutable method and evidence/result storage or effective writable source scopes. The shared `ac_fs_boundary.overlaps_existing` compares actual device/inode identities along both ancestor chains, including existing parents of future paths, so filesystem case aliases are identified without string case folding or probe writes. Parent aliases cannot turn a read-only declaration into writable storage, and inaccessible observations fail without effects. A changed manifest/member/owner or
population fails before the dependent operation. The cooperative filesystem
boundary does not claim protection against hostile concurrent administration.

The native admission implementation binds the shared filesystem helper's exact
hash and rechecks its bytes before each installed-method boundary check. A
helper change therefore invalidates that selected implementation rather than
silently changing its meaning. The fixed supervisor module inventory also
includes the helper; old, missing or changed helper pins fail currentness.

The caller's request cannot supply a policy, installed root, replacement target
basis or success receipt. Startup policy remains trusted operator configuration;
its selection is not a new admission or operational grant. The final external
cohort binding identifies A without requiring source embedded in A to contain
A's own future manifest digest.

## Public setup

```sh
python3 AC_ROOT/build_tenants/graphify/examples/fd-support/prepare_readonly.py \
  --profile stdo-3.0.5-rc.1 --product-root PROJECT --definition-name Product.json \
  --method-installation INSTALLED_305 --out NEW_SETUP
```

Setup uses actual `stdo status --verify`, then emits read-only configuration and
public requests. It registers no work grant or executor. Existing legitimate
work policies add the same installation binding to their actual owner/grants;
the [native admission recipe](fd-support-stdo-3.0.1.md#real-work-policy-operator-recipe)
retains its mechanism, authority and source-acquisition requirements, with this
new exact target instead of its historical 3.0.1 selection. `tools.describe`
returns actual supported operations; native `results.conjoin` is refused.

Focused tests cover old-profile conservation, installed/member/owner mismatch,
request override, long-lived stale binding, missing issuer/recipient grants,
uncertain retry and a real controlled-process severity return. They establish
contract mechanics; actual installed-A and Codex/Claude scenarios are separately
retained qualification evidence.
