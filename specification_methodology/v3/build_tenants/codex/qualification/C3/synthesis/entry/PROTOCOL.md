# Ordinary Entry and Cold Continuation Trial

The subject is post-selection use of a frozen source candidate through its
unmodified `stdo-work` entry. It is not an installed-v3 acceptance trial. The
installed 2.5.1-rc.2 builder remains the construction authority. An authentic
host `stdo status --definition ... --verify` receipt, the exact Product
Definition and export inventory bind that authority and the candidate under
test. The receipt is never described as an installed v3 release.

The root activation selects the final source cut before paid execution. The
actor receives the ordinary skill entry location, the task location and the
disposable workspace boundary. It chooses subsequent material using actual
Read, Glob and Grep calls. No task frame, route answer, oracle or expected edit
set is supplied in its prompt. A refusal at the declared candidate-selection
boundary is an observed limit, not silently bypassed or scored as completion.

## Inputs and independence

The task and original workspace are copied without changes from the independent
`D1-ordinary-discovery-probe` case in the synthesis oracle. Only the task and
workspace fields reach the actor; expected outcomes, forbidden behavior and
rationale remain host-side. The package is exported at one immutable commit
into `/private/tmp`; neither the working repository nor live user directories
are granted as actor input.

This harness Writer authored the six domain-profile repairs but did not author
the tested core, `stdo-work` route or the independent task/oracle. Harness
construction and result checking are not an independent whole-method review.

## Sequence

1. Export the frozen package and copy the task workspace to an isolated root.
   Record initial hashes, the selected definition and authentic verification,
   candidate identities, tool constraints and input limits.
2. Start a fresh Claude CLI process with only Read, Glob and Grep. Give the
   normal entry, task and workspace paths; require exact proposed edits and a
   result. Preserve the native tool requests/results and their byte measures.
3. Check that proposed paths and contents satisfy the grant before host effects.
   The host deliberately applies only the proposed `deploy/env.example` edit,
   if valid. It persists the actual first return, the selected application
   boundary and the applied/unapplied coordinates in the fixture's durable
   trial records. This is a controlled partial application, not a provider
   crash, interrupted inference or assertion that the actor applied its edits.
4. Start a different fresh Claude process, with no resumed session or prior
   private context, on the same continuing workspace and ordinary skill entry.
   It can read the durable task, first return and host application record. It
   observes current files and proposes the remaining work. No workspace reset
   or oracle is supplied.
5. The host validates and applies permitted proposals, compares actual files
   with the independent oracle, and records retained progress, outstanding
   work, actual discovery and failure/stop behavior. If these two calls need
   no repair, the third call repeats the original D1 task through rc.2's
   installed ordinary entry, with its complete compressed acquisition path
   available and the same model, tools, task and limits. Otherwise that call
   is reserved for one diagnosed harness repair or required bounded follow-up;
   it does not erase prior observations. One matched task does not establish
   general superiority.

## Execution and measurement

Each native call has a 120,000-byte selected prompt/tool-material allowance,
15-minute wall allowance and USD 2 provider ceiling. At most three calls and
USD 6 are reserved. Input measurement includes the supplied prompt and the
UTF-8 tool-result material returned to the actor; requested source paths,
offsets, limits and source sizes are also recorded. Repeated tool acquisition
counts again. Provider system prompts, hidden processing and model attention
are not measured by these counters. Provider token usage is reported separately.

The CLI runs in safe/restricted mode with session persistence disabled and
only the three read tools enabled. Candidate files and task files are readable;
the actor has no write, shell, service or network tool. Host execution records
the native tool population and rejects unexpected tools or paths. The native
transcript, actual material counter and provider limits determine whether an
activation fits the declared envelope; exceeding it invalidates the fit claim
and stops further dependent execution. The final return discloses any inability
to account for tool-result material rather than substituting a prompt-only
measurement.

Host proposals are applied only to the original task's permitted files after
path containment and exact allowed-change checks. Trial records are host-owned
fixture metadata. No proposal can change the package, oracle, controls or live
repository. Outputs contain no credentials or live-user file contents.

## Claims and limits

The trial can establish native discovery from the declared ordinary entry after
experimental source selection; dependent-file discovery on D1; preservation of
persisted partial work; and cold continuation using current files and durable
results. It cannot establish installed-release bootstrap, universal context
sufficiency, provider-crash recovery, concurrent-write recovery, remote effect
reconciliation or whole-method superiority. Acceptance and the source-port
review policy remain outside this activation.
