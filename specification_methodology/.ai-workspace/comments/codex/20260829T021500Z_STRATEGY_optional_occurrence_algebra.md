# STRATEGY: Optional Occurrence Algebra Over Mutable Reality

**Author**: codex

**Updated**: 2026-08-29T05:49:11Z
**Status**: Draft commentary
**Size boundary**: strategy only; exact constitutional contracts and qualification evidence belong to separately selected work

## Purpose

This post proposes an optional `a_c` model-family profile for reasoning about
fresh traversal applications over mutable reality.

It does not:

- amend the pure Axiomatic Calculus;
- amend the pure Reference Frame method;
- select a Product change, ticket, release line, carrier, runtime, or
  implementation;
- define a complete occurrence specification; or
- qualify any downstream interpretation.

The post owns eight strategy proposals:

1. occurrence semantics belong in an optional model-family profile rather than
   every `a_c` signature;
2. an occurrence is one immutable traversal-application identity, not a
   snapshot of the world;
3. event admission follows an acyclic candidate, judgment, admitted-event, and
   relation-materialization dependency;
4. admitted framework events are immutable facts about an application or
   governed subject;
5. current occurrence state is a projection over an exact admitted-event
   frontier;
6. repeated application creates a fresh occurrence over the then-current
   mutable subject; and
7. causal subgraphs and wider typed lineage remain distinct; and
8. prospective Reference Frame semantics are a separate optional profile, not
   part of occurrence algebra or pure Reference Frame law.

The record names and relation groupings below are illustrative candidate shapes
supporting those proposals. They are not mandatory law. Exact kinds, fields,
cardinalities, predicates, judgments, stops, and residuals are closure
obligations for future, separately authorized specification and qualification.

## Current Disposition

**REVISED CANDIDATE for review as a strategy and triage basis only.**

The direction is useful because it states the missing relation between an
immutable application history and an evolving mutable subject. The earlier
draft was too large and had started to become a shadow specification. This
revision retains the algebra, ownership boundary, central identity proof, and
downstream-interpretation boundary. It deliberately defers exhaustive relation, judgment,
constraint, and carrier contracts.

No source acceptance, Product adoption, implementation, or release follows
from this post.

## Event Admission Identity DAG

The central identity law must be acyclic.

A candidate contains pre-admission relation claims, not relations sourced by a
future admitted event:

```text
FrameworkEventCandidate = (
  candidate content,
  source frontier,
  subject binding,
  optional occurrence,
  relation-claim inventory,
  source authority,
  evidence,
  basis
)
```

Each direct relation claim contains one canonical endpoint role:

```text
this_admitted_event
```

Exactly one endpoint uses that role. Every other event endpoint must already
exist in the candidate's source frontier. Every non-event endpoint must resolve
under the exact profile basis and subject scope.

Admission proceeds in one direction. `prec_id` below means “is an identity
content prerequisite of”; it is not semantic causation:

```text
claim prec_id candidate prec_id admission judgment
      prec_id admitted event prec_id materialized relation
      prec_id successor frontier

candidate content
  -> candidate identity c
  -> unchanged admission judgment j(c)
  -> admitted-event identity a(c, j, admission basis, authority)
  -> materialized relations r_i(a, claim_i)
  -> successor frontier f_(k+1)
```

Therefore:

- `c` contains no `a`;
- `j` targets unchanged `c`;
- `a` contains no relation identity whose own content contains `a`;
- each `r_i` is created only after `a` exists;
- `claim_materialized_as` retains the claim-to-relation derivation; and
- the successor frontier is distinct from the candidate's source frontier.

For example:

```text
supports_event(existing_event, this_admitted_event)
event_causally_precedes(existing_event, this_admitted_event)
corrects_event(this_admitted_event, existing_event)
event_for_occurrence(this_admitted_event, occurrence)
```

The source frontier makes the admission identity dependency well-founded and
lets each relation enforce its own declared acyclicity without using timestamp,
storage position, or a total event order as semantic cause. It does not make
the union of all typed event relations one DAG.

The profile basis identifies one empty initial frontier. A first event may
terminate its lineage at its source authority and admission judgment; it does
not need an invented earlier event merely to justify admission.

## Occurrence Identity

An occurrence is exactly one application of one exact traversal:

```text
OccurrenceIdentitySeed = (
  occurrence-profile basis,
  occurrence kind,
  traversal identity,
  functor kind,
  stable subject binding,
  existing input observations,
  intended typed outcomes,
  semantic authority,
  application authority,
  optional operation grant,
  evaluation authority,
  decision authority,
  context,
  owner,
  scope,
  evidence contract,
  stop contract,
  invalidation law,
  unique issuance coordinate
)
```

Produced observations, result, effect invocation, effect evidence, evaluation,
correction, and closure do not enter the seed because they do not yet exist.

Exactly one `application_of_traversal` relation binds the occurrence to the
traversal in its seed. Applying the same traversal again creates a fresh
occurrence identity even if actor, input, output, timestamp, or effect bytes are
equal.

Containment, correlation, continuation, retry, re-entry, and causation remain
separate relations. A preserved lineage coordinate does not collapse two
applications into one occurrence.

## Event Frontier And Projection

An event frontier is an exact finite governed inventory:

```text
EventFrontier = (
  profile basis,
  admitted-event inventory,
  inventory digest,
  projection law,
  context,
  owner,
  scope,
  authority
)
```

At successive frontiers:

```text
E_evt,k subseteq E_evt,(k+1)
```

Earlier admitted bytes and identities do not change. A later correction adds
another event.

For occurrence `o`:

```text
P_k(o) = project_occurrence(B_fw, o, f_k)
```

`P_k(o)` is an exact judgment subject containing effective relations, state,
supporting-event identities, and residuals under one projection law. It is a
read model, not runtime authority, mutable controller state, or a workspace
snapshot.

`P_(k+1)(o)` is a distinct subject even when its effective value equals
`P_k(o)`. A judgment binds one projection identity and frontier; it cannot
silently follow stable occurrence identity to a later frontier.

Competing corrections without declared precedence remain conflict residuals
or refuse. Arrival time, ordinal, or carrier order cannot choose the winner
unless competent authority declares that coordinate as an exact precedence
input to the projection law. The coordinate itself acquires no decision
authority.

## Mutable Effect Reality

`W` is mutable external reality. It may be a workspace, process, repository,
database, environment, external system, or another effect surface.

The core relation is:

```text
W_n
  -> observe and bind A_n over current W_n
  -> bind intended typed outcome B_n where the traversal contract declares one
  -> open fresh occurrence o_n for F_K[v](A_n) -> Y_n | Omega_n
  -> when Y_n requires an external effect, construct separate invocation
       x_n = (op_effect, executor, actor, g_effect, target, territory)
  -> the authorized executor performs op_effect over only that territory in W
  -> W_(n+1)
  -> observe bounded post-effect evidence
  -> evaluate the declared transition A_n -> B_n
  -> any retry or continuation that reapplies a traversal opens fresh o_(n+1)
     over current W_(n+1)
```

Any seed-bearing `B_n` resolves before `o_n` is minted. An intended outcome
derived only after `Y_n` exists is excluded from that seed and enters later
through a separately admitted fact.

`F_K` classifies the traversal application. It does not identify or perform
`op_effect`. Traversal, functor kind, operation, executor, actor, grant, and
effect invocation remain separate coordinates.

An in-place operation over external `W` is not thereby the `a_c`
transformation `T[t]`. If a downstream profile also models it as a calculus
transformation, `t` must be exact, its input model remains unchanged, and its
output is only a proposed successor under AC-013.

Each iteration is a fresh immutable traversal occurrence over evolving
terrain. The occurrence identity-dependency graph and each relation explicitly
declared causal are acyclic. The wider typed lineage need not be one DAG and may
contain opposing edges of different lawful kinds. A traversal topology or
lifecycle may iterate without reusing an occurrence identity.

The following distinctions are constitutional candidates for a selected
profile:

```text
immutable observation event != immutable observed subject
effect evidence              != effect-owner state
occurrence projection        != workspace snapshot
event replay                 != complete reality reconstruction
typed result                 != mutable state carrier
checkpoint                   != active workspace
```

A snapshot or checkpoint may be evidence or a recovery input under downstream
authority. It changes reality only when an authorized effect applies it and a
later observation admits what now holds.

The effect owner, effect executor, actor, admission authority, evaluation
authority, and decision authority remain distinct coordinates. The executor
may mutate only territory named by the exact operation grant. Partial effect is
evidence and residual pressure; it is not rewritten as no effect.

## Causality And Typed Lineage

For one frontier:

```text
G_k = (V_k, C_k)

V_k = admitted occurrence identities in scope
C_k = effective causally_precedes relations
```

The effective occurrence-causation graph and the event-causation graph are
separately acyclic. Their edges are not unioned with support, correction,
correlation, continuation, retry, re-entry, or evaluation edges to manufacture
one universal DAG.

```text
event_causally_precedes != causally_precedes
event_correlates        != event_causally_precedes
supports_event          != event_causally_precedes by default
continuation            != retry
retry                   != re-entry
lineage ancestor        != material cause by default
```

Occurrence causation is never inferred from timestamps, ordinals, storage
positions, adjacency, equal labels, shared inputs, containment, or correlation.

Lineage is the wider typed explanation graph. Its foundation is stratified:

| Relation stratum | Lawful terminal |
|---|---|
| candidate claim | candidate source authority and source frontier |
| admission | unchanged admission judgment and admission basis |
| materialized relation | exact claim plus admitted-event identity |
| effective projected fact | admitted supporting events at the bound frontier |
| authority, basis, or import | owning authority or basis record |

A lineage witness returns typed edges and exact terminals, not only an ancestor
label. A cycle within a relation declared acyclic, an identity-dependency
cycle, an unowned terminal, or a material-cause claim with no admitted support
refuses. Opposing edges of different lawful kinds—such as an earlier event
supporting a later correction that points back to it—do not constitute a causal
cycle merely because an untyped union would loop. Unknown physical causes
remain outside the framework boundary rather than being invented.

## Separately Owned Prospective-Frame Profile

Prospective semantics do not belong in `Sigma_occurrence` or pure Reference
Frame law.

A separately owned optional profile may import exact accepted Reference Frame
and `a_c` bases and define:

- an expected semantic graph;
- required observation capabilities;
- a population-construction relation;
- realization and evidence frontiers;
- membership and closure law;
- provisional-view policy; and
- invalidation and reactivation law.

Its graph overlay may exist before any workspace or other effect surface is
realized or bound. The overlay defines a **semantic horizon**: types,
relationships, constraints, and observations that may or must become meaningful.
Derived sensor requirements name observation-capability types, not concrete
sensors. The overlay supplies no claim about when, where, or how a subject,
sensor, observation, or result will exist.

The four prospective coordinates remain distinct:

- **semantic horizon** — the intensional expected graph;
- **realization frontier** — the exact cutoff of realized and bound subjects;
- **evidence frontier** — the exact evidence admitted for this frame
  evaluation, distinct from the occurrence profile's `EventFrontier` even when
  it references one; and
- **closure frontier** — the exact cut at which the activated evaluation's
  closure law may return one closed result under its bound authorities.

Advancing one does not silently advance another.

The lifecycle remains:

```text
profile available
  -> Product adopts exact profile
  -> Product declares a frame and binding basis
  -> construction derives a candidate population subject
  -> ordinary Reference Frame activation binds exact actor and grants
  -> evaluation returns one closed result
```

These are not interchangeable states.

Construction grants no authority, and its candidate population result has no
evaluation, operation, or decision authority. Any material constructor executes
only under an existing owner-issued operation grant over the exact subject and
territory. Activation must bind the unchanged frame, exact evaluation, current
subject and basis, actor identity, capability evidence,
semantic/evaluation/operation/decision grants, evidence-acquisition boundary,
and invalidation law.

An expected type, relation pattern, or observation-capability requirement may
exist before realization. It does not mint a future member, sensor,
observation, occurrence, evidence, or result identity.

Similarity of names, successful execution, or a commentary example cannot

## Qualification Falsifiers

A selected occurrence-profile work item should at least falsify:

1. collision or shadowing of any inherited `a_c` identity;
2. a semantic-object sort missing any inherited `SemanticObject` field;
3. a relation, constraint, latitude, residual, traversal, transformation, or
   judgment wrapped as a semantic-object value or stripped of required fields;
4. a candidate containing its future admitted-event identity;
5. an admission judgment targeting changed candidate bytes;
6. a materialized relation that differs from its pre-admission claim;
7. a cycle in the identity-dependency graph or a declared causal relation;
8. opposing lawful support and correction edges rejected merely because their
   untyped union forms a loop;
9. a first admission that incorrectly requires an earlier event;
10. duplicate admission of one candidate under one profile;
11. two traversal applications collapsing to one occurrence;
12. a subject-scoped event forced into a convenient occurrence;
13. timestamp, ordinal, adjacency, containment, or correlation creating cause;
14. a projection judgment silently following an occurrence to a later
    frontier;
15. competing corrections selected by arrival order;
16. effect evidence, result payload, checkpoint, or projection becoming the
    mutable state carrier;
17. a functor kind, traversal, domain operation, executor, actor, or effect
    invocation substituted for another;
18. mutation outside the exact operation grant;
19. partial effect rewritten as no effect;
20. untyped lineage or a lineage witness with no lawful terminal;
21. a prospective declaration minting future subject or sensor identities;
22. construction masquerading as frame activation or evaluation;
23. Product adoption inferred from profile availability;
24. semantic horizon, realization, evidence, or closure frontier silently
    substituted for another;
25. two unrelated downstream interpretations importing one another's domain
    identities; and
26. a downstream mapping claiming losslessness while omitting one of its own
    application, event, basis, retry, projection, or authority distinctions.

Representative examples support review. They do not become an interpreter,
runtime, or new authority surface.

## Decision And Re-Entry

The recommended direction is to keep two proposals separate:

1. optional event-derived `Sigma_occurrence`; and
2. optional prospective-frame profile.

Current goals and tickets select neither. If Product authority chooses either,
the smallest honest re-entry is a separate `product_reprice` work item with its
own basis, identity, requirements, qualification, acceptance, and release
relation.

The occurrence work item must turn the algebraic sketch into exact record,
relation, judgment, constraint, stop, residual, projection, and interpretation
contracts. The prospective work item must define its imported bases,
expectation signature, adoption relation, population construction, activation,
closure, and invalidation law.

Do not put those contracts back into this strategy post. Link to the selected
authority surfaces when they exist.
