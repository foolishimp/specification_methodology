Applications, concepts and comparison with industry practice

30 November 2022

A conversational starting point

Project record

Before the project work

The project lineage begins in mid-2024. No application or methodology work is assigned to this earlier period.

Concepts and comparison

The conversation becomes a place to build

ChatGPT provides the starting point for the industry timeline. A conversation could carry a problem description, a proposed implementation and successive corrections. That made an interactive route into software construction visible well before the project’s first surviving applications.

The later history repeatedly encounters the limits of that arrangement: where the intended behaviour is recorded, how a change preserves existing relationships, and how a new session establishes what has actually been done. Those are the questions used to read the lineage. They should not be projected backward as a fully formed methodology in 2022.

Industry releases in this period

30 November · ChatGPT

ChatGPT launched as a research preview using a model from the GPT-3.5 series. Its conversational interface supported follow-up instructions, explanations and code examples. Launch announcement

About the dates and comparisons

Historical cut: 23 November 2026, Australia/Sydney. The timeline begins with ChatGPT’s launch in November 2022. Project work began in mid-2024. Its endpoint is the stripped-down STDO Builder replacing ABIogenesis in the work being prepared for release as STDO 3.2 today. The latest published method release verified for this account is 3.1.0-rc.3; the intended 3.2 release and Builder’s local 0.1.0 cut remain separately identified.

Follow the continuous overview of industry releases and software lineage beside the detailed project commentary, comparisons and diagrams. The source retains industry, project and concept sections for each period. Industry entries are selected milestones relevant to this lineage, rather than a complete model catalogue. Comparisons are historical interpretations of dated sources, not measurements of industry adoption or claims of influence. They distinguish convergence, extension, divergence and reconsideration. A different vocabulary can describe a shared idea; a similar vocabulary can conceal a different scope.

2023

Agents, evaluation and declarative programs

Project record

An existing body of techniques

These publications precede the surviving application and C4H records. They are part of the environment in which the later exploration took place.

Concepts and comparison

Several ingredients already existed

Role specialization, tool use, evaluation and declarative composition were already explicit research and engineering concerns. This matters when reading C4H and Genesis: assembling agents into stages, adding a reviewer or drawing a graph cannot by itself establish a new idea.

The useful comparison is more specific. What did the project make an explicit part of the work? Which relationships did it try to preserve? What happened when an implementation failed to meet the intended conditions? Later project terms such as assurance, criticality and delta need to be compared at that level, rather than counted as inventions because their names differed.

Evaluation itself therefore predates this lineage. The historical question is how evaluation developed from checking an output into a continuing relationship between requirements, implementation, observation and correction.

Mid-2024

Exploration becomes application work

Project record

Mid-2024 · Work begins

Work began through conversational exploration and AI-assisted implementation. A Mural replacement became the first application in the development account, later preserved as Brain Dump / MyPostit.

20 August · discover_build

The earliest surviving implementation found in this investigation combines FAISS retrieval, sentence embeddings and AutoGen agents for topic refinement and code execution. First check-in

Concepts and comparison

Learning through construction

The starting activity aligned with a practical use of the tools: ask for a working application, inspect what appeared, and iterate. The retrieval and AutoGen experiment also directly used an existing agent framework. This is a clear instance of adopting industry techniques.

The applications then supplied problems that a better prompt alone did not settle. A system could be locally plausible while its state, history or relationships became inconsistent. That experience would give the later method its recurring concern with preserving meaning across a change.

The dates need separate treatment. ChatGPT and Claude did not first launch in mid-2024. That is the beginning of this work, following their 2022 and 2023 introductions. The August experiment is the earliest recovered implementation; the whiteboard is the first application identified in the development account. Neither establishes the first day an idea was considered, and no direct code transfer from discover_build to C4H has been established.

September 2024

Brain Dump and Chain of Thoth

Project record

15 September · Brain Dump / MyPostit

A scaffold and the first substantial TypeScript application were checked in on the same day. The application provided an infinite canvas, movable notes, arrows, storage, import/export and an event-history interface. Application check-in

17 September · Chain of Thoth

The next project explicitly introduced command/query separation and event sourcing. Its Rust backend represented notes, arrows, groups and embedded boards, with an event store, snapshots and collaborative sessions. React and Flutter clients followed. Preserved source

Concepts and comparison

Relationships survive only if changes preserve them

The whiteboard was a concrete exercise in relational state. Moving a note also had to preserve its arrows. The commit history records lost connections, positioning problems and a Claude 3.5 refactor. These are useful historical observations because they expose the gap between producing code and preserving a working system through successive edits. Development history

Chain of Thoth made change itself explicit. Commands changed the board; queries observed it; recorded events supported its history. This adopted established software techniques. Event sourcing had been described long before 2024, including reconstruction of state from recorded changes. Earlier account of event sourcing

The significance within this lineage was the experience those techniques provided. State, change and an account of what happened became separate engineering concerns. Later runtime projections and evidence records revisit that distinction, although continuous reuse of the original code has not been established. The presence of undo, snapshots or a log also does not establish that every historical state could be replayed correctly.

October–December 2024

From thought units to C4H

Project record

20 October UTC · refactorer

The first check-in, dated 21 October in Sydney, used specialized AutoGen agents for intent, scope, analysis, refactoring and testing. A coder4h_config.yaml file placed the C4H name in this precursor.

The retained Chain of Thoth design described a Unit of Thought: intent, constraints, execution, verification and feedback. Design bridge

3 November · c4h_intent_system

Discovery, solution, refactoring and verification formed an intent-driven workflow. Events carried root, parent and branch relationships. Early implementation

31 December · C4H monorepo

The first commit explicitly reinitialized a monorepo. Earlier implementations had already explored AutoGen, LiteLLM and Prefect. Consolidation

Concepts and comparison

The work unit acquires intent and scope

A note represented thought on a board. The proposed Unit of Thought made it a bounded activity: something with an intention, constraints, a construction step and a way to return feedback. The retained Thoth document supplies an explicit bridge into the coding-agent work.

The multi-agent structure aligned with AutoGen and MetaGPT, which already provided relevant precedents. C4H’s particular emphasis was on carrying the meaning and lineage of a work request through several transformations. An execution identifier, its parent and its originating intention were becoming part of the design, rather than context left entirely in a conversation.

This also exposed a lasting design choice. A workflow can constrain the stages while an agent chooses how to perform a stage. Anthropic’s December distinction between workflows and agents provides a contemporary comparison; C4H’s later forms and the 2026 Builder repeatedly redraw that boundary.

The surviving C4H implementations provide firm October and November anchors. The broader exploration began earlier in mid-2024. Treating the December monorepo creation as the invention date would erase its precursors; assigning all later C4H capabilities to mid-2024 would go beyond the recovered record.

Concepts and comparison

Making specifications usable in work

C4H Manager supplied more than a chat entry point. Its editor could create, version and reuse work orders; select team and runtime configurations; submit a job; and inspect its results. The specification-building function at this stage was the preparation of usable work orders and configuration for execution. The preserved source supports that description without implying that it was already the later STDO specification system. Manager capabilities

The microfrontend architecture separated the shell, configuration editing and job management. Subsequent requirements moved from the initial Module Federation approach toward dynamically imported ES modules. The later AI MFE Portal carried that interface exploration forward. Architecture and usability were part of the lineage alongside the construction agents. Architecture requirements, Portal origin

The homeostatic proposal ran beside this practical work. Its question was what supplies a system’s reason to act, as distinct from the mechanism that reasons about an action. This was a conceptual proposal inspired by biological models; it was not yet an implemented evaluation framework. The distinction becomes important as the terminology later moves into software assurance and feedback.

Assurance becomes part of construction

Project record

17 May · C4H SDLC methodology

The documented process distinguished its interface, declarative methodology and reference implementation. Its Assurance Team could run tests, review changes with an LLM against intent and standards, involve a person, and send problems back to solution design or coding. Methodology

Concepts and comparison

Evals, under the language of assurance

The assurance stage is a concrete overlap with what the wider field called evaluation. A candidate was compared with criteria; several forms of judgment could contribute; a failed assessment could cause another construction attempt. C4H expressed that in the language of development teams, intent and assurance.

There is no need to place the project ahead of evaluation research to explain the contribution. OpenAI Evals had been public since 2023, and the December 2024 evaluator–optimizer pattern already described feedback between generation and review. C4H was applying these concerns to a work order moving through a development lifecycle.

The source also records interaction with the changing industry tools: the May process explicitly contemplates Claude Code performing construction within a stage. This is evidence of integration with a contemporary coding agent. It shows a move away from having to implement every coding action inside C4H.

Concepts and comparison

A game becomes a model of a difficult software system

Psychic Blob was a direct driver of specification-methodology development in this lineage. Its complexity was structural: skills carried memories; memories affected personality; a body’s capacity constrained which skills could be used; composing an avatar changed several related properties at once. The game made it necessary to describe what those relationships meant before judging whether an implementation preserved them.

The first architecture separated a portable TypeScript core from its user interface and divided responsibilities among character, state, world and other modules. The July cognitive model pursued memory, affect and coherence in more detail. These supplied both a demanding application and a way to explore constraints and emergence. They did not establish a general scientific theory of cognition. Game architecture, Cognitive model

The semantic-transformation paper made the engineering question explicit: requirements and design add specificity while preserving meaning inherited from intent. Its proposed formal account is an ancestor of STDO’s authority chain. The record establishes that proposal, rather than a proof that every LLM-generated transformation satisfies it.

Kiro provides a useful contemporaneous comparison. Both lines were making requirements and design explicit before implementation. The local exploration also asked how constraints and meaning survive across layers and interacting components. That was a broader explanatory ambition, with a correspondingly larger burden of definition and evidence.

The July homeostatic account concerned an automated organisation. It was a proposal, not proof of a deployed self-regulating system. Its importance here is the conceptual transfer: a discrepancy becomes a reason to act, and its importance affects which work should happen next.

A public account of how LLMs reason

The July paper proposed soft unification: attention makes graded, context-dependent matches across overlapping local structures, with symbol-like behaviour emerging from continuous representations. It drew on constraint satisfaction, Prolog and Markov blankets while distinguishing partial neural matches from strict symbolic unification. Those were proposed explanations of model behaviour, with the existence and reliability of the suggested boundaries still open to testing. Paper

The engineering consequence was already visible in its proposed architecture: combine a probabilistic LLM with explicit constraints, symbolic checks and a controller. Reasoning capability and the source of an agent’s intent were separate questions. Alongside the industry’s longer reasoning traces and stronger coding agents, this work pursued a structural explanation and the design of a system around the model. It supplied a research thread that later fed the ontology and returned to practical specification work; it did not establish a new model architecture or a measured performance advantage.

Concepts and comparison

A method can outlive an individual agent

C4H had implemented a development process. AI SDLC increasingly treated the process as a reusable subject in its own right. The explicit ai_init import establishes one of the clearest transfers in the chain: application practices became a shared baseline, then part of a methodology.

The timing shows substantial alignment with industry tooling. Kiro and Spec Kit made specification-led work visible in products; Agent Skills packaged procedural knowledge; long-running-agent designs used files and Git to bridge sessions. The project’s context management, development skills and continuity records addressed related needs. Reusability and persistent project guidance were shared concerns by this period.

The distinctive question continuing from the semantic model was what a transformation must preserve. A set of instructions can guide an agent, but a method also needs to say what authorizes a decision and what would establish that its result is acceptable. The later STDO work makes those obligations increasingly explicit.

Runtime feedback added another part of the homeostatic loop to the codebase. Observation could expose a discrepancy after construction and feed it back into development. The check-in proves an implementation existed; it does not establish deployment, operational reliability or coverage of every relevant kind of drift.

The comparable industry and project publications establish convergence. Except where a dependency or integration is recorded, timing and resemblance do not establish which work influenced the other.

Concepts and comparison

Research becomes a reusable constraint specification

The papers make the research branch visible between the software projects. The earlier reasoning account helped frame the ontology; the ontology then fed a revised account of reasoning. Logical Encapsulation, published as Programming LLM Reasoning, turned those ideas into a four-layer template: constraints, ontology, algorithm and operating principle. The intended use was to declare the assumptions and criteria under which a model should work. Reasoning revision, Template

The Political OS suite applied the approach outside software development. Competing political frameworks became explicit specifications with different primitives, invariants and evaluation procedures. Its place in this history is as a worked application of reasoning under a declared basis; its political conclusions are not needed to establish the software lineage. Published suite

From judging an output to governing a continuing loop

The homeostatic thread can now be followed through distinct records: the March 2025 intent-layer proposal; May’s assurance stage; July’s sensed/reference state and criticality; December’s runtime-feedback implementation; and the January–February requirements and delta model. These are related developments, not interchangeable names for a single unchanged mechanism.

The engineering interpretation became more precise. Requirements supply conditions for the intended product. Observations describe the product as it stands. Evaluation identifies where the two do not agree. The resulting work may change the implementation, design or specification, according to where the problem belongs.

Genesis applied a common operation to requirements, designs, code and tests:

iterate(Asset, Context[], Evaluators) → Asset'

Human judgment, probabilistic model work and deterministic functions became explicit categories, later written as F_H, F_P and F_D. Graphs and metric-driven refinement already had precedents in DSPy and LangGraph; the synthesis here applied construction and evaluation across lifecycle artifacts. Genesis account, LangGraph’s 2024 introduction

The ontology supplied a broader vocabulary for persistence, boundaries and meaning. Its claims about physics or cognition remained research proposals. The engineering model can use constraints and feedback without requiring those broader claims to be established. Likewise, the term homeostasis does not establish that the implemented loop is stable or that its evaluators are valid.

Concepts and comparison

Deciding which layer owns the rule

The split exposed three different responsibilities. An engine executes work and records its events. A lifecycle says what development activities mean. A method says which source governs a decision and what counts as an acceptable result. A common vocabulary does not make those responsibilities identical.

ABIogenesis used a compiler analogy: an earlier installed engine could build its successor. Its original intent even proposed GTL as the requirements surface. Later work restored requirements and design as separately owned sources. That is a genuine change of position about how much meaning an executable declaration should own.

The method’s independent repository resolved a practical authority problem. Installed standards had previously depended on which product supplied them. An explicit source and immutable release could now govern implementations without being defined by whichever engine happened to run.

This aligned with industry’s increasing attention to harnesses and orchestration, but pursued a different level of abstraction: a method intended to survive replacement of the harness itself. The cost was more concepts and boundaries to keep consistent. The later stripped-down Builder should be read against both the benefit and that accumulated cost.

A March Genesis decision had emphasized satisfying invariants while leaving the construction path flexible. Subsequent method work qualified that position: equivalent final output does not erase an obligation concerning authorized effects, causal order or necessary evidence. Recorded decision

Concepts and comparison

A passing result is a claim about something specific

C4H had asked which operation produced an output. STDO 2 also asked which subject an observation concerned, under which basis, and what conclusion it could support. A component test, a substitute execution path and an installed product outcome were different subjects. Evidence about one could not silently qualify another.

Reference frames made the distinction explicit: purpose, subject, governing basis, authority and evidence determine the judgment. Satisfied, falsified, indeterminate, outside the frame and invalid basis preserve differences that a single pass/fail label can hide. Missing observation is different from an observed failure.

This extends evaluation practice into rules for interpreting and reusing a result. It does not establish that industry evaluation lacked such distinctions; the project made them general obligations within its own method. The separate question is whether an implementation actually observes them.

The geometry correction is an equally important part of the history. An earlier world-model account required a geometric construction where an institutional or software entity might have adequate identity and evidence without one. Version 2.2.2 made the entity the primary semantic unit and geometry an optional overlay. A useful explanatory model had become too broad a requirement.

The research publications show a corresponding change in the explanation. July’s Emergent Reasoning v4 retained positive results about semantic structure alongside failed boundary tests. It distinguished candidate representations from demonstrated Markov objects and separated proposal, evaluation, verification and admission. The connection to STDO is a shared design question: what evidence and authority are needed to accept a probabilistic proposal? Published revision

The ontology’s September repository revision further separated constraints, dynamics and evaluation. An allowed structure does not necessarily form or persist, and a claimed Markov boundary needs a declared, tested screening property. This revision follows the July v2 publication; the two are distinct records. Research counterexamples narrowed the account. Published v2, Repository v3

Concepts and comparison

Keeping the constraints and reducing the framework

Builder is a deliberate simplification of the preceding approach. It retains a graph of permitted work, explicit checks and evaluation, and an account of what the framework did. It gives the agent freedom to work inside a step, including choosing its own retries and undo operations.

The mutable workspace is the source of truth about the work. Each step reads it as it stands. The framework supplies references into it, keeps no copies of its content and does not freeze, reconstruct or roll it back. Its log records decisions and events; passing checks against the actual workspace is what closes a transition. The log does not substitute for the result.

This converges with a longstanding industry preference for simple agent compositions and with file-based continuity across sessions. The retained method graph supplies a specific governance boundary. Simplicity was already explicit in Anthropic’s December 2024 engineering account; Builder’s reduction should therefore be understood as a local change informed by accumulated experience, without presenting minimal agent harnesses as a new invention.

There is also a concrete divergence. Anthropic’s April Managed Agents account separated a durable session log, an agent harness and replaceable sandboxes. Builder specifies one address space and treats the current workspace as truth, with a log limited to the framework’s own events. Both separate responsibilities; they place persistence and recovery in different parts of the system. The choice answers a particular product’s needs rather than establishing a universal advantage. What the exploration changed

The chain is not a steady march from less capable to more elaborate systems. It includes adoption of existing techniques, application-driven extensions, attempts at broader foundations and later removal of mechanisms that had become too prescriptive.

The durable thread is the relationship among intent, construction, observation and correction. The main refinements were to make the subject and basis of a judgment explicit, preserve meaning through transformations, and return a discrepancy to the layer entitled to resolve it. Builder carries those concerns into a smaller operating model. Whether that model delivers the intended reliability remains a question for evidence from its actual use.

STDO 3.2A method. A smaller Builder.

Specification, Ticketing, Design and Outcome-Driven Development

Specify the outcome. Govern the work. Evaluate what was built. Continue from the product as it stands.

Release preparation · 23 November 2026

Build what was agreed

STDO provides a method for turning an intended product into an implementation and keeping the two in agreement as work continues. STDO Builder carries that method into an agent’s work: a person describes the outcome, the framework selects permitted steps, and the agent constructs and revises the product.

The 3.2 direction brings the accumulated method together with a smaller Builder. Requirements and design remain explicit. Evaluation remains part of the work. The framework operates over the files that actually exist, leaving the agent room to solve the task inside each permitted step. Intent

The method and the Builder

The method defines the governing relationships: agree what is wanted, design how it will be realized, construct it, and evaluate the result against the applicable conditions. A discrepancy can return work to the requirement, design or implementation that needs to change.

The Builder executes a declared graph of that work. A node names an asset and its required state; a transition says what work may follow; a graph function names how that transition is performed. The framework determines which step may run. The agent chooses how to perform the work within it.

The workspace holds the product: its specification, design, code, tests, evaluations and work records. Each new session reads the current files. A ticket carries the request, delivered work, decisions and binding rulings; Git carries the detailed changes. A single event log records framework events. Product definition

From a request to an accepted change

  1. Set up the product. Select its method and put the graph and Builder settings into an empty or existing workspace.
  2. Describe the work. Write a ticket in ordinary language. The first step determines where the change enters the graph and proposes its scope.
  3. Confirm the direction. Read the proposed work and the files a decision concerns. A ruling can carry a constraint through subsequent sessions.
  4. Construct and evaluate. The agent works on the selected step. A separate session evaluates the result where required, then deterministic checks read the workspace.
  5. Accept or revise. Answer where the graph requires a human decision. Unresolved findings lead to further work or a stated stop.
  6. Continue from the result. A later change or resumed run starts with the current workspace. Work follows the dependencies affected by the change.

The supplied getting-started guide records this sequence on a small command-line product, including a later change and a resumed run. It is one concrete example, not a prediction of the time or cost of another product. Worked guide

A smaller boundary around the agent

The framework is deterministic; the agent’s construction need not be. This separates the question of whether a transition is permitted from the question of how a model will produce a useful result.

The framework passes references to workspace files, keeps no copies of their content and checks the files as they stand. It records its own events without attempting to reconstruct everything the agent did within a step. Each ticket has a working branch, but the agent’s workspace on that branch remains mutable.

This is the architectural change from ABIogenesis: the construction framework has a narrower purpose and a smaller account of state. It keeps the method’s constraints while leaving more implementation activity to the coding agent. The reduced boundary also makes limits visible. A refusal can stop further work without undoing a change already made. Restoring or correcting files remains work to perform in the workspace. Guard rails

Decisions remain visible

STDO does not treat a plausible artifact as sufficient acceptance. The request, applicable conditions and evidence need to refer to the same work. A person can inspect the result, reject it with a reason and record a ruling for subsequent sessions.

The Builder distinguishes construction, evaluation and deterministic checks. Those functions have different evidential roles: a passing structural check cannot answer a question it did not test, and an evaluation is a judgment whose basis matters. The graph determines which are required for a particular step.

Its intended outcome is a product built to its specification. The current cut’s findings show why that outcome still needs scrutiny: permitted work can exceed the desired amendment inside an asset, and detection of a protected-file change does not restore the file. Findings at the cut

A first working session

After installing a matching Builder release and its prerequisites, the supplied CLI workflow starts with setup, a ticket and a run:

stdo-builder setup repo/hello --name HelloCli
stdo-builder ticket repo/hello "a command-line Hello World in JavaScript with two tests"
stdo-builder run repo/hello

When the run asks for a decision, inspect the files it names. Accepting can also record a constraint:

stdo-builder answer repo/hello yes --ruling "Use only Node's standard library."
stdo-builder run repo/hello
stdo-builder show repo/hello

The current package requires Node.js 24 or later, Git, the STDO method release manager and a configured command-line agent. The installation page and getting-started guide describe the actual package and its prerequisites. These are local source links; no public STDO 3.2 download is claimed by this draft.
