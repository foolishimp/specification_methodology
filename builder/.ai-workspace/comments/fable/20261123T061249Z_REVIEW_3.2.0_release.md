**Words used.** The *workspace* is the folder that holds the product being built; I also call it the *product folder* where it lies inside a *larger repository*, a git repository whose top folder is above it. A *ticket* is the work order. For each ticket the framework makes a *branch* named `stdo/<ticket>` and a *checkout* of it: a second folder, at `.stdo-builder/local/checkouts/<ticket>/` inside the workspace, in which git writes the branch's files (git's own word is worktree). *Main* is what the product calls the branch the user's own folder is on. A *session* is one start of the agent; the *stand-in agent* is a part of the product that writes fixed files in place of an agent. A *run* is one start of `stdo-builder run`. The *start commit* is the commit a run makes first, with the message "what the user changed by hand on main". The *method release* is a published cut of the STDO standards; `stdo` is the method's own program that installs one. The *Builder release folder* is `stdo-builder-3.2.0/`; the *bundle* is the folder `stdo-3.2.0/` that holds it together with a copy of the standards and a history; the *download* is the bundle as one `.tar.gz` file. A *manifest* is the file that lists every file of a release with its sha256.

Counts: severity 1: none. Severity 2: two. Severity 3: eight. Severity 4: ten. Severity 5: five.

## Severity 2

### R-1. "Main" is whichever branch the user's folder is on when a command is given; a ticket follows the user from branch to branch, is merged into each and reported each time as "merged into main"; inside a larger repository, work committed on the other branch is then left out of main while git counts it as merged

- **Severity.** 2. It breaks the owner's sentence on the repository's other branches and the product definition's "merged into main". The only way round it is never to change branch while a ticket is open, which no page says.
- **Reviewed.** `src/flows/workspace.ts:352-365` (`open`: at every command the branch the folder is on is read and called `main`); `src/kit/three_way_merge.ts:152-155`; `src/flows/run.ts:135` (the ticket's branch is taken up again under whatever `main` then is); `src/flows/merge.ts:70, 95`; `src/kit/three_way_merge.ts:326-349` (below the top of a larger repository the merge commit has the branch checked out and the ticket's branch as its two parents, and takes the product folder's files alone); `src/library/library.ts:197` (the words "its branch is merged into main, at …").
- **Claim it breaks.** The owner, in ticket `261123-001543-eae1`: "It leaves as they are every other file of the repository, what the user has not committed elsewhere in it, and the repository's other branches." `PRODUCT.md:91-92`: "Each is built on a branch of its own and merged into main when its work is done." What set-up prints (`library.ts:161`): "…the repository's other files, what is not committed outside the folder and its other branches are left as they are." `packaging/INSTRUCTIONS.md:72-74`: "changes none of the repository's other branches". The one sentence a user has on the matter is `INSTRUCTIONS.md:76-77`, "Main is the branch the repository's own folder has checked out, whatever its name"; it does not say that this is read anew at each command, nor what a change of branch then does.
- **Evidence.** Three scratch repositories (the first two of 307 files, by `S/scripts/mkbig.sh`, with the product in `products/hello`), a ticket made active on `main`. In each the user then does what a developer does many times a day: makes a branch of their own and commits on it.
  1. `W/big-sw`. On the user's branch `topic` the answers and runs go on, and the last run prints "The work on the ticket … is done. It lies in the done lane and its branch is merged into main, at 5ae2dcb…". `5ae2dcb` is a commit on `topic`; `main` did not move. Back on `main` the ticket is still active, and a run there merges the same ticket a second time (`c5c3853`) and prints the same sentence. The event log holds two entries "run ended … done … the ticket is merged" for one ticket.
  2. `W/big-sw2`, work left out. The user's commit `14faed4` on `topic` adds one line to `src/app/app1.js`, outside the product folder, and an unfinished note inside it. The run on `topic` takes `topic` into the ticket's branch: the commit's own message says so, `6cf86f2 merge topic into stdo/…`, while every printed sentence says "main". Back on `main`, the run merges the ticket's branch into `main` (`737dfcf`). That merge commit has `14faed4` among its ancestors and holds the product folder's files alone, so `main` now holds the user's unfinished note and does not hold the line in `app1.js`. When the user later merges `topic` (`d28ba21`), git takes `14faed4` as merged already: `git merge-base --is-ancestor 14faed4 main` exits with 0, `git show main:src/app/app1.js` holds no line of it, the merge brought one other file only, and `git branch -d topic` then removed the branch without complaint. The line is in no file of main; it is still in the history, for someone who notices and brings it back by hand. Git gave no warning, and the framework said "merged into main" twice.
  3. `W/top-sw`, the product is the whole repository. The user's unfinished file `extras/draft.txt`, committed on `topic` alone (`779cd60`), is on `main` after the run there merged the ticket (`887ecf4`): content that nobody accepted, and that the user had not asked to merge.
  No test has the user change branch in the workspace's own folder. The one guard there is, `three_way_merge.ts:330-331`, can be removed with every test passing (R-10).
- **What depends on it.** Every user who changes branch in their own folder while a ticket is open; in a larger repository, the committed work of their other branches.
- **Smallest repair.** Take main's name once, when the ticket's branch is made, and refuse a command given while the folder is on another branch.

### R-2. Each ticket is built in a second copy of the workspace, against guard rail 2 and the owner's recorded ruling "git, no copies!"; the copy lacks what git ignores, is never removed, and the user's own folder may not be changed while a session works

- **Severity.** 2. By my reading it breaks guard rail 2, and a break of a guard rail is a hard stop; the first reviewer left the question unjudged (its check 10), and so did the review of the round that brought it in. The owner's ruling settles it either way.
- **Reviewed.** `src/kit/three_way_merge.ts:238-250` (`git worktree add`); `src/flows/run.ts:130-135`; `src/services/sessions.ts:62` (a session's working folder is the checkout); `FLOWS.md:23` and `:67-69`; `packaging/INSTRUCTIONS.md:79-82, 140-142`.
- **Claim it breaks.** `INTENT.md:21-22`: "The agent does the work, in one workspace: the folder that holds the product being built." `INTENT.md:29-30`, guard rail 2: "The workspace is mutable. The framework never freezes it, copies it or rebuilds it in order to work on it." The owner, in ticket `261123-001543-eae1`: "The workspace is that folder, and it is still one workspace."
- **Evidence.**
  1. How it came in. Commit `0247cb97c` (18 November, 21:38, "proposal for the product definition: several active tickets, each on a branch … A proposal for the product owner to accept or undo") replaced the product definition's "One session works in one workspace at a time, on one ticket at a time." by "Each is built on a branch of its own and merged into main when its work is done. One session works on a ticket at a time." The Executive's guide of that evening, `.ai-workspace/comments/claude/20261118T083428Z_GUIDE_specification_round_three.md:110`, under "New defaults, each mine, for the owner's ruling", lists "A ticket's checkout is kept inside the workspace", names the conflict with guard rail 2 and with "one workspace: the folder", and records: "Ruled by the owner, 18 November: 'git, no copies!'. I read it as: branches and their checkouts are git's, and the framework itself copies no file." Commit `cb73970b1` (22:38) made that reading a law (`FLOWS.md:67-69`: "A branch and its checkout are made by git and by nothing else"). The independent review of that round said (`.ai-workspace/comments/opus/20261118_REVIEW_specification_round_four.md:31`): "Whether rail 2's 'copies it ... in order to work on it' and the intent's 'one workspace: the folder' admit a checkout per ticket is the owner's to confirm." I found no record at `c4ff4efee` that he confirmed it. His words say no copies; the law says a copy is allowed where git makes it at the framework's command. C-17 is the same kind of fault in other sentences.
  2. It is a copy, made in order to work on it. For each ticket the framework has git write every tracked file of the workspace a second time, and starts every session there. The user's own folder receives the work only at the merge. The question put to the user names the copy: "Do you accept code at .stdo-builder/local/checkouts/261123-154016-b5fb-the-comment-at-the/build_tenants/main/code, as it now stands?" (`stdo-builder show W/m1c`).
  3. It is rebuilt. The copy holds only what git tracks, so what the workspace holds that git ignores (installed dependencies, local settings) is made again in each copy. Builder's own check does so: `tests/run.sh:4` installs the dependencies where `node_modules` is absent. In the workspace where the product's own tickets were run (`/Users/jim/src/apps/stdo-builder-self/ws/builder`, read only): nine tickets in 18 hours left nine checkouts of 157 to 161 MB, 1.4 GB in all, each with its own `node_modules` of about 155 MB, beside a repository of 8.6 MB.
  4. The user's folder is held still. While a session works in the copy, a change by the user to a file of the product in the workspace's own folder stops the run (R-13).
  5. Nothing removes a copy (R-16), and nothing built needs one: only one ticket is active at a time in this release (`src/flows/run.ts:60-61`, `const LIMIT = 1`; in `W/m4` a run for a second ticket ended "refused", log line 111), so the ticket's branch could be checked out in the workspace's own folder.
- **What depends on it.** Guard rail 2 and the model's "one workspace"; disk and time per ticket for any product with dependencies; R-11, R-13 and R-16 follow from it.
- **Smallest repair.** The owner rules whether a checkout per ticket is a copy under guard rail 2; if it is, the ticket's branch is built in the workspace's own folder.

What a user does read is `INSTRUCTIONS.md:52-53`, "an existing system, which is left where it is", and `:96`, "A file that is there already is left as it is."

### R-4. The published download does not install where tar keeps every member as a file: it holds two files the manifest does not name

- **Severity.** 3.
- **Reviewed.** `stdo-3.2.0.tar.gz` as published; the bundle's `install.sh`; the assembler `release/bundle.sh`, which makes no tarball (the command that made it is recorded nowhere).
- **Claim it breaks.** Bundle `INSTALL.md:8`: "To install: `sh install.sh <folder>`". `origin/main:README.md:7-10`.
- **Evidence.** The tarball has 1,125 members, 972 of them files; the manifest names 969 and is itself the 970th. The two more are `stdo-3.2.0/history/._history.html` and `stdo-3.2.0/history/._history.md`, 176 bytes each: the side files macOS tar writes for a file that carries extended attributes (both history pages carry `com.apple.lastuseddate#PS`). macOS tar (bsdtar 3.5.3) folds them away again on extraction, so the release installs on the machine that cut it (`S/dlx`). Extracted with every member kept as a file (`S/scripts/untar_plain.py`, into `S/dlx-gnu`; this stands in for GNU tar, which I could not run), `sh install.sh` prints "not in the manifest: history/._history.html" and "not in the manifest: history/._history.md", exits with 4 and installs nothing. The tree of the tag `stdo/v3.2.0` does not hold the two files (it compares equal to `S/dlx`, 970 files).
- **What depends on it.** Every install from the download on Linux.
- **Smallest repair.** Make the tarball with `COPYFILE_DISABLE=1`, by a script under version control, and run the install from the tarball as the last step of the cut.
