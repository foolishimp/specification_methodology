# No. Second review of the 3.2.1 candidate of STDO Builder (build 3.2.1-rc.7): bug report

**Verdict: no.** Finding V-1 is repaired: in every trial I ran, a session that cleans the folder, or whose record is removed or damaged, ends in a question to the user, and nothing is committed before the answer. I found no defect of severity 1 or 2 that the four tickets (V, Y, Z, X) brought in, and no guard rail that their work breaks. The claim fails on its third part. The words the release's note will carry say that whatever a session changes outside its step is put to the user before anything is judged or committed, and that what a session commits is asked about too. ## 3. Findings

### Q-1. A session that puts the folder on main and commits there gets what it changed outside its step into the ticket, judged and merged, with no question

- **Severity.** 2. The consequence is V-1's: the check the work is judged by, and the agents' instructions, are what a session made them, and no ruling is asked. By the reading the first review gave V-1 it breaks guard rail 1: two ordinary git commands of the agent's make the framework take the agent's changes in as the user's. No intent to get round the framework is needed: an agent whose instructions, the project's or the user's own, say to commit work on main does this. It is narrower than V-1 in one way: the run names main as changed, so a user who then reads main's history can find the commit. I do not count that an adequate way round. The words ask nothing, say "none holds the ticket", and tell the user how to go on; and a real session's commit bears the git identity its commands find, which is the user's own (in my trials it bears the trial's). I did not measure how often an agent commits on main.
- **Not brought in by the four tickets.** rc.4 does the same (item 4). It has been open since a session works in the user's own folder. In release 3.2.0 a session worked in a checkout apart, where git refuses to check out a branch another working tree holds; that is reasoning from git's rule, and I did not run 3.2.0.
- **Reviewed.** The installed build, in a repository of its own. Three things meet. The framework compares the folder with the session's start (`compare`, `src/flows/changed.ts`), so what a session committed on another branch is not in the comparison. Main is taken into the ticket's branch at the start of each run, wherever it moved (`takeMainIn`, `src/flows/merge.ts`; REQ-FLOW-008 step 1, `FLOWS.md:978`). And a change among the branches while a session worked is named and asks nothing (REQ-FLOW-001, `FLOWS.md:145-153`; `INSTRUCTIONS.md:295-301`). The requirement's own acceptance tries main "moved by a commit that changes no file" (`FLOWS.md:231-233`); a commit that changes a file is tried nowhere. The Executive's notes on ticket X try a session that moves main to its own commit on the ticket's branch, where the stray file is asked about; they do not try a commit made on main.
- **Claim it breaks.** The note, rule 2: "Whatever differs in the folder outside what the step writes is put to the user, who rules before anything of the step is judged or committed." The note: "so what a session commits is asked about too." REQ-FLOW-005 (`FLOWS.md:740-743`): "Until the user has ruled on what changed while a session worked (REQ-FLOW-006), the framework judges nothing on the ticket, commits nothing on it, starts no session on it and merges nothing". REQ-FLOW-001's acceptance (`FLOWS.md:228-230`): "A session changes a file of the workspace outside what its step writes: the framework makes no commit, on the ticket's branch or on main, that holds that change before the user says yes to it." The packet the framework gives every session: "anything else that differs when this session is over … is named to the user, who rules on it before anything of the step is judged or committed."
- **Evidence.**
  1. The session stays on main: `sh E/my/trials/m9.sh` (`E/my/out/m9.commitonmain.txt`). The session writes its three files and strays as in V-1's trials (the check's command set to `true`, a line added to `AGENTS.md`, `left-by-a-session.txt` written). Then `git checkout main`, `git add -A .`, `git commit`, and it returns. Run 2 exits 1: "The run stopped … the workspace's folder is on the branch main, which is not the ticket's … Put it back on stdo/…, git switch stdo/…; nothing is committed, judged or started on the ticket until then." and "While the session on write-specification worked, these changed among the repository's branches, tags and stash; it may have been the session or you, and none holds the ticket: main (changed)." The user gives that `git switch` and starts a run, as those words and the page say (`INSTRUCTIONS.md:410-414`). Run 3 exits 0 and asks only "Do you accept intent … as they now stand?", adding "Every other file of intent, product and requirements is as it was when main last held it": the session's work is now shown as main's. The ticket's branch holds all three changes, by the framework's own commit `d8f5861 STDO Builder: merge main into stdo/…`. After two ordinary yeses the ticket is done. The event log has "the tests pass = yes" for write-build, with the check run as `true`. "main holds: left-by-a-session.txt: yes | the session's line in AGENTS.md: 1 | main's graph runs the command checks as: the tests pass = true". "rulings on what changed in the ticket: 0 | runs that asked for a ruling: 0".
  2. The session comes back to the ticket's branch after its commit on main: `sh E/my/trials/m1.sh straygraph "fix+straygraph"` (`E/my/out/m1.straygraph.txt`); here it commits on main only its change to the graph. No stop at all. Run 2 asks the ordinary acceptance and adds the one line "… none holds the ticket: main (changed)." The next run takes main in (`6a93655 STDO Builder: merge main into stdo/…`, whose second parent is the session's commit); the event log has the check "the tests pass" of write-build as yes in 0.013 seconds, run as `true`; the ticket is done; 0 rulings. The same with a line in `AGENTS.md` (`m1.sh straymain`).
  3. The control: the same three strays left in the folder on the ticket's branch end in "The run waits for your ruling", naming all three (the kit's case `control`, section 1).
  4. rc.4: `sh E/my/trials/m9.sh sb4` ends the same way (`E/my/out/m9.commitonmain.rc4.txt`), and so do the other two (`E/tv4/out/`).
- **What depends on it.** Rule 2 of the note holds only while no session commits on the branch the ticket left. The run already knows the two things that matter here, that a session worked and that main moved while it did: it prints them.

### Q-2. A git repository of its own that a session leaves in the folder is never put to the user; the framework commits a pointer to it

- **Severity.** 3. Material but bounded: it needs a session that clones or makes a repository inside the folder, as `git clone` of a library does. What depends on it: main then holds a pointer to a commit that no clone can follow, so the product as merged is not the product as it stood in the user's folder; `git status` in that folder shows nothing; and one sentence of the instructions (Q-3 c).
- **Not brought in by the four tickets.** rc.4 does the same (item 2).
- **Reviewed.** The installed build, in a repository of its own. `differenceNow` and `identitiesOf` in `src/kit/content_addressing.ts` drop each path git lists with a `/` at its end; the comment at line 99 says "A path that ends in "/" is a repository of its own inside the folder; it is no file of this one." `commit` in `src/kit/three_way_merge.ts` stages with `git add -A`, which takes such a folder as a pointer to a commit (mode 160000). A search of the requirements, the design pages, the source, the tests and the Executive's notes finds the case nowhere else; the first review's triage lists a product "with submodules" as not covered.
- **Claim it breaks.** `INSTRUCTIONS.md:248-251`: "the run compares every file git does not ignore in the workspace's folder with what was there when the session started. Where a file differs that the step does not write … it waits, and asks you to rule." REQ-ALG-008 (`ALGORITHMS.md:400`). REQ-FLOW-001's acceptance, as quoted under Q-1. The note, rule 2. The intent's outcome "The result can be verified from the workspace alone", for anyone who has the repository and not the user's folder.
- **Evidence.**
  1. `sh E/my/trials/m1.sh nested "fix+nestedrepo"` (`E/my/out/m1.nested.txt`). The working session of write-specification makes `vendor/lib/` with one file and gives `git init`, `git add -A`, `git commit` there. Run 2 asks the ordinary acceptance; no run's words hold "vendor". At the end main holds "160000 commit 980b4ae… vendor/lib", brought in by the framework's commit `2bf08bc STDO Builder: step write-specification: the user is asked`; "rulings on what changed in the ticket: 0 | questions on what changed: 0"; "git status at the end:" is empty. Main holds no `.gitmodules`. A clone of main has an empty `vendor/lib`, and there git says "fatal: no submodule mapping found in .gitmodules for path 'vendor/lib'"; the user's folder has `lib.js`.
  2. rc.4: the same (`E/tv4/out/m1.nested.rc4.txt`).
  3. Inside the place a step writes its code in: no silent pass there. The step cannot close, run after run: "write-build could not close: the same number of checks failed twice in a row. What did not pass: verdict, code." where the code's folder is itself the repository (`m5.sh`), and "What did not pass: verdict." where the repository lies below it (`m5b.sh`). No word says why.
  4. A repository with no commit, as `git init` alone leaves (`m1.sh nestedempty`): the run stops with git's own words, "git refused: error: 'scratchrepo/' does not have a commit checked out", and each run after is refused with them. Once the user removes that folder the run goes on (`m10.sh`).

### Q-3. The note, and one sentence of the instructions, promise what Q-1 and Q-2 show the product does not do

- **Severity.** 3. What depends on it: what a reader of the note believes the release guards. These are its central promises. They become so if Q-1 and Q-2 are repaired; if those are put off, the words must say so.
- **Reviewed.** The note at `b80eb173e`; `INSTRUCTIONS.md` of the release as cut, which is the installed page byte for byte.
- **The sentences, and where each fails.**
  - a. Rule 2: "Whatever differs in the folder outside what the step writes is put to the user, who rules before anything of the step is judged or committed." Not so in Q-1 and Q-2, nor in Q-6. Not so for a change of a file's mode alone: `AGENTS.md` made executable by a session is committed and merged, "100755 blob … AGENTS.md" on main, with no question (`m1.sh chmodx`).

### Q-5. A symbolic link to a folder, or one whose target is not there, that appears while a session works stops the run with git's own words; each run and answer after is refused until it is gone

- **Severity.** 4. Limited and local: the stop names the path, and there is a practical way round, which I tried (`m10.sh`): once the user removes the link, or has git ignore it, the run goes on. No page says so. A build that leaves such a link reaches it, as a Python environment on Linux, Bazel and Nix do. It was so on rc.4 (`E/tv4/out/m1.symdir.rc4.txt`).
- **Reviewed.** `differenceNow` gives each new or changed path to `git hash-object`, which follows a link.
- **Claim it breaks.** `INSTRUCTIONS.md:416-417`: "A file that changed while a session worked, outside what its step writes, does not stop a run: the run waits for your ruling on it".
- **Evidence.** `m1.sh symdir`: "The run stopped …, at write-specification: git refused: fatal: Unable to hash t/m1-symdir/hello/spec-link. Put right what it names, then start a run again." Then each `answer` exits 4 with git's words, and each `run` exits 2, "The run is refused before any step". `m1.sh symdangling`: "fatal: could not open '…/dangling-link' for reading: No such file or directory". `m1.sh symstep`, the link inside what the step itself writes: the same stop. Controls: a link to a file is asked about as "agents-link.md (added)" and committed after the yes (`m1.sh symfile`); a link to a folder that the user makes while no session works, or commits before the ticket, stops no run (by hand; the products are `E/my/t/m4-userlink` and `m4-linkbefore`).
