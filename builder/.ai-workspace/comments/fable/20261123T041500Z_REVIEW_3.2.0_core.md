**Words used.** A *node* is a part of the product that the graph names (intent, product definition, requirements, design, tests, code). A *vector* is a kind of step that writes one or more nodes, for example `write-code`. A *ticket* is the work order. Its first step is the *induction*: a session writes the *triage* into the ticket (its kind, its class, the node the work *enters at*, the node it ends at, and its *term*, the list of vectors that carry it out), and the user confirms it. A *session* is one start of the agent: a *working session* writes, an *evaluating session* judges and writes a verdict of yes, no or cannot. A *step* is one attempt at one vector. A *check* is a test the graph declares of a node, such as a command that must exit with 0. A *run* is one start of the command `stdo-builder run`. *Main* is the line the user's own folder is on. A ticket's *checkout* is the folder `.stdo-builder/local/checkouts/<ticket>`, which holds the ticket's branch and in which its sessions work. A *resolution* is a line the framework adds to the ticket for each yes or no of an evaluation or of the user, with the commit that holds what was judged. An *identity* is the hash git gives to the content of a file or folder. The *packet* (the code calls it the brief) is the file a session is started with. *Protected files* are the files a session may not change; `trespass` is the function that compares them before and after a session. The *hold* is the lock file a run keeps while it works on a ticket. A run is *cut off* when its process ends without ending the run: the user's Ctrl-C, a closed terminal, a crash. The *stand-in agent* is the product's own substitute for the agent, which writes fixed files. *S1* is the product's first scenario: set up and build the smallest product, called Hello. `REQ-…` names a requirement, and `D` with a number a decision in `design/DECISIONS.md`.

Counts: severity 1: none. Severity 2: one. Severity 3: eight. Severity 4: nine. Severity 5: four.

## Severity 2

### C-1. A session that is cut off with its run is never checked for the files it may not change; what it changed is committed and reaches main with no word to the user

- **Severity.** 2. It breaks guard rail 1, so by the review rules it is a hard stop.
- **Reviewed.** `src/flows/run.ts:136-149`: what an interrupted step left in the checkout is committed as "the result of an interrupted step". `src/flows/run.ts:199-208`: whatever lies uncommitted in main's own folder when a run starts is committed as "what the user changed by hand on main", and this happens before the run looks for a cut-off run (`run.ts:163-167`). `src/flows/step.ts:309-313`: the only place `trespass` is asked, after a session has returned or failed. `FLOWS.md:24` (REQ-FLOW-001) itself calls whatever is uncommitted on main "what the user left uncommitted".
- **Claim it breaks.** Guard rail 1: "It controls the agent; the agent never controls it." `PRODUCT.md:93-95`: "The agent writes the product's assets and the framework writes its own files; neither writes the other's." REQ-ALG-008: the settings file, the governing graph and every asset the vector does not write are protected. REQ-FLOW-001, law (`FLOWS.md:61-63`): the framework adds to main only a move on the board, "what the user changed by hand" and a merge.
- **Evidence.**
  1. `E/p2`. The working session of `write-code` wrote the code, and also `.stdo-builder/settings.json` (the agent's command became `sh -c "echo the agent rewrote the command the framework runs"`) and `.stdo-builder/graph.json` (the command of the check "the tests pass" became `true`). I killed the run before the session returned. The next run: line 91 `run cut off`, line 92 `commit made … what an interrupted step left`, then a working session, an evaluation that said yes, and the question. The question named one changed line of `code/hello.sh` and said "Every other file of code is as it was when main last held it." After `answer yes` the ticket merged (line 112). `git show main:.stdo-builder/settings.json` gives the session's command, and `git show main:.stdo-builder/graph.json` gives `"argv": ["true"]` for that check. No entry of the log holds the words "protected" or "may not", and no line printed names either file.
  2. `E/m2`. The session wrote into main's own folder: a new file `build_tenants/main/code/extra_tool.sh` and a line added to `hello.sh`. I killed the run. The next run: line 92 `commit made … what the user left uncommitted on main`, then line 93 `run cut off`. The question said "hello.sh: 1 line changed (1 added, 1 taken out), and 3 lines remain as they were. Every other file of code is as it was when main last held it." One of the three lines that "remain" is the session's, and its new file is not named. After `answer yes`, `git show main:build_tenants/main/code/extra_tool.sh` gives the session's file, and main's history holds it under the commit "what the user changed by hand on main".
  3. `E/p3`. The cut-off session changed `specification/INTENT.md`. The next run named no file. The induction's check of the term said "the user has not accepted intent as it now stands; enter at intent", two induction sessions were started on that finding, and the run stopped with "induct-ticket could not close: the same number of checks failed twice in a row" (lines 91 to 118).
  4. By trace only: a line that a cut-off session writes in the framework's part of the ticket is read as it stands, since that part is compared only inside `trespass` (`src/algorithms/trespass.ts:105-106`).
- **What depends on it.** Every run the user interrupts while a session is at work. No intent to get round the framework is needed: a session that edits the check that fails it, and an ordinary Ctrl-C, are enough. Afterwards main's settings and graph can be what a session wrote, and nothing shows it.
- **Smallest repair.** Before committing what a cut-off session left, compare the protected files of both folders with the last commit the framework made on each line, and stop as after any session.
