**Words used.** As in the first report: a *node* is a part of the product that the graph names (intent, product definition, requirements, design, tests, code). A *vector* is a kind of step that writes one or more nodes, for example `write-code`. A *ticket* is the work order. Its first step is the *induction*: a session writes the *triage* into the ticket (its kind, its class, the node the work *enters at*, the node it ends at, how much it touches, and its *term*, the list of vectors that carry it out), and the user confirms it. A *session* is one start of the agent: a *working session* writes, an *evaluating session* judges and writes a verdict of yes, no or cannot. A *step* is one attempt at one vector. A *check* is a test the graph declares of a node. A *run* is one start of the command `stdo-builder run`. *Main* is the line the user's own folder is on. A ticket's *checkout* is the folder `.stdo-builder/local/checkouts/<ticket>`, in which its sessions work. A *resolution* is a line the framework adds to the ticket for each yes or no. An *identity* is the hash git gives to the content of a file or folder. The *packet* (the code calls it the brief) is the file a session is started with. *Protected files* are the files a session may not change; `trespass` is the function that compares them before and after a session. The *hold* is the lock file a run keeps while it works on a ticket. A run is *cut off* when its process ends without ending the run. The *stand-in agent* is the product's own substitute for the agent. *S1* is the product's first scenario, which builds the smallest product, Hello. The *workspace* or *product folder* is the folder that holds the governed product; it may lie inside a *larger repository*. New here: the *registry* is the file `.stdo-builder/registry.json`, which lists the graph functions a vector can carry out; the *stretch* of a ticket is the set of nodes between the node it enters at and the node it ends at; `well_formed` is the function that accepts or refuses a graph before a run; `show` is the command that prints where the work stands; a *process group* and a *session of processes* are the operating system's two ways of grouping processes, and a signal sent to a group reaches only the processes still in it. `C-n` and `R-n` name findings of the first and the second report; `REQ-…` names a requirement and `D` with a number a decision in `design/DECISIONS.md`.

## Severity 2

### G-1. The processes of a session are not ended when its run is interrupted, and not all of them at its time limit or at its return; they go on writing, the next run starts a second session beside them, and what they write later is blamed on another session or committed as the user's and merged

- **Severity.** 2. It breaks guard rail 1, so by the review rules it is a hard stop.
- **Reviewed.** `src/kit/supervised_child.ts:61-67`: the agent is started with the platform library's defaults, which make it the leader of a process group and of a session of processes of its own (`node_modules/.pnpm/@effect+platform-node-shared@4.1.4_effect@4.1.4/node_modules/@effect/platform-node-shared/dist/internal/nodeChildProcessSpawner.js:2`). `supervised_child.ts:81-85`: the only thing that ever signals that group is the closing of the scope the agent was started in (the same package, `dist/NodeChildProcessSpawner.js:359-377, 419-434, 488-503, 520-526`); the scope closes when the agent's own process ends or its time is over. `src/programs/cli.ts:20-24, 67` and `src/library/library.ts:81-87`: a command's work runs as a promise of its own, so when the run's process is interrupted the platform's handler ends the process (`@effect/platform-node-shared/dist/NodeRuntime.js:11-31`) and that scope is never closed; there is no handler for a closed terminal. `src/flows/run.ts:163-168`: the next run writes that the session "was cut off with it" without looking whether its process still runs. `src/services/sessions.ts:62`.
- **Claim it breaks.** Guard rail 1: "It controls the agent; the agent never controls it." `PRODUCT.md:92-93`: "One session works on a ticket at a time." `PARAMETERS.md:18`: "Sessions at work on one ticket | 1 | At any moment". `FLOWS.md:18`: the framework "ends one that runs longer than allowed". `FLOWS.md:501-503`: "A session that run started and that neither returned nor failed was cut off with it". `FLOWS.md:70`: "Runs share nothing but the workspace."
- **Evidence.** In each trial the agent's command was a shell script that starts two more processes: one in its own process group, and one that makes a session of processes of its own, as a server or a watcher does. Every process number was kept (`C/out/k*.pids`) and I ended each by hand afterwards.
  1. *The run is interrupted.* Four ways, each on a new workspace: the interrupt signal sent to the run's process group, as Ctrl-C in a terminal does (`C/ws/k1b`, `C/out/check1.k1b.observed.txt`); the terminate signal sent to the run (`k2`); the hang-up signal, as a closed terminal sends (`k3`); the kill signal (`k4`). In all four, four seconds later the agent's process, now a child of process 1, and both processes it had started were alive, and each had gone on writing a line a second into the checkout (7 lines before the signal, 11 after). The run printed nothing, and its hold file was left.
  2. *What the next run makes of it* (`C/ws/k1`, `C/out/k1.run2.txt`, `k1.run3.txt`). The run after the interrupted one wrote line 43, `run cut off … a session it started that neither returned nor failed was cut off with it`, while that session's three processes were alive. It committed what they had written so far as "what an interrupted step left" (line 44) and started an evaluating session beside them (line 46): two sessions at work on one ticket. What the first session's processes wrote during the three seconds of the evaluating session was then reported as that session's doing: "the evaluating session of write-build changed protected files: build_tenants/main/code/heartbeat.txt, build_tenants/main/code/heartbeat2.txt" (line 49), and the same again in the run after (line 56). The work went on only after I had ended the three processes by hand (line 57 onward).
  3. *The session's time is over* (`C/ws/k5`, the vector's time set to one minute in the workspace's graph). Line 43: `session failed … it ran longer than allowed and was ended`. The agent and the process in its group were ended. The process in a session of its own was not; what it wrote next was reported as "the evaluating session of write-build changed protected files: build_tenants/main/code/heartbeat2.txt" (line 48).
  4. *The session returns in the ordinary way* (`C/ws/k6`). The working session started the two processes and returned with exit code 0 after two seconds. The process in its group was ended at the return. The other one wrote, twenty seconds after the session had returned and after the user had been asked (line 53), one file into the checkout's code and one into main's own folder. The next run committed the second as "what the user left uncommitted on main" (line 56) and the first as "what an interrupted step left" (line 57), judged again and asked again; after the user's yes both files are in main: `git -C C/ws/k6 show main:build_tenants/main/code/late.txt` and `…main:specification/LATE.md`, under the commits `6eb5774` "the result of an interrupted step" and `2ec9c35` "what the user changed by hand on main". No line printed and no entry of the log says that a session wrote either.
  5. *Real sessions do start such processes.* By the agent program's own records, 17 of the 49 sessions started with the present command used the shell tool's option that runs a command in the background (48 of all 393, and ten started a process with `&`), `C/out/scan_sessions2.txt`, `scan_sessions3.txt`. On this machine the same agent program starts every shell command as the leader of a session of processes of its own: the shell of my own commands has a process group of its own number and the state `Ss`, and the agent program is in another group. So the process "in a session of its own" of items 3 and 4 is the ordinary place of a command a real session starts, not a contrived one. What the agent program does with such processes when it is itself ended I did not test; in item 1 it is not ended at all.
  6. *No scenario and no test has a session that outlives the framework.* Scenario S2 reads "The user: kills the framework and the session, then starts a run." Its test kills one process (`tests/scenario_driver.ts:230-235`), and the stand-in session runs inside that process (`src/services/stand_in.ts:68`). See G-6.
- **What depends on it.** Every run the user interrupts while a session is at work, every session that reaches its time limit, and every session that leaves a process behind it. After an interrupt the agent itself works on in the checkout with no time limit, since the timer ended with the framework, and the next run starts a second session in the same folder. C-1 reported what a cut-off session had left before the next run started; this is what it goes on to write afterwards, which is then reported against whichever session is at work (as in R-13 for the user's own edit), or enters main as the user's change (R-3).
- **Smallest repair.** Keep the number of the agent's process group with the hold; before a session is started, when a session's time is over and when it returns, end what is left of that group and of the processes it started, and start no session while any of them is alive.

## Severity 3

### G-2. The ticket is not in the graph: one vector is marked `first`, and what rests on the inducted ticket, what its words reopen and what the induction must write are cases in code; a vector holds neither what it rests on nor what it writes

- **Severity.** 3.
- **Reviewed.** `src/graph/terms.ts:161-175`: a vector holds its name, the mark `first`, results and checks (the first vector only), an evaluation, a decision, attempts, minutes, frames and a `function`; it holds neither its source (what it rests on) nor its termination (what it writes). `terms.ts:57-60`: what it rests on is worked out. `src/method/registry.json`: what it writes is the `writes` of the registry entry that `function` names. `src/algorithms/passes.ts:417-420`: a record kept at the node the ticket enters at stands also for the ticket's words. `src/algorithms/next.ts:44-48, 54-61`: the first vector comes before every other, and is left out for a ticket marked as the simplest. `passes.ts:304, 354, 359` and `src/flows/gather.ts:132-134`: the ticket's fields `enters`, `ends`, `term` and `simplest` are read by those names. 47 lines in twelve source files ask `first === true` (`passes.ts` 13 times, `brief.ts` 9, `well_formed.ts` 8, `step.ts` 3, `show.ts` 3, `terms.ts`, `next.ts`, `gather.ts` and `question.ts` 2 each, `trespass.ts`, `take_up.ts` and `workspace.ts` 1 each). `src/flows/setup.ts:71, 81, 93, 123-125`: set-up names the nodes design, tests and code. `tests/graph.test.ts:211-231`.
- **Claim it breaks.** The owner's words on structure: "source and termination, as in category theory", and, when the graph had been turned into positions on a line, "wtf - is this prose?": what depends on what, what order and what reopens are data in the graph, never an order in a list, a naming convention, a sentence or a case in code. `GRAPH-LANGUAGE.md:86-88`: "The nodes and what each depends on are the graph's edges. Nothing else in a graph states a dependency". `GRAPH-LANGUAGE.md:103-108` (REQ-GRAPH-004): "What a step means, when it is done and what follows it are declared in the graph. The framework's code holds no rule about a particular node, vector, asset or governed product."
- **Evidence.**
  1. *A dependency that no edge states.* Every step of a ticket depends on the inducted ticket. Trial `C/ws/td`: after the intent had been accepted, I added one sentence to the ticket's words on main; the next run made a new induction session (line 103), asked again, and after the yes started the working session of `write-intent` again (line 122). The graph holds no edge that says so, because the ticket is no node; the dependency is the code `...(enters === at ? [ASKED] : [])` at `passes.ts:420`.
  2. *A rule about one particular vector.* The graph says of the induction only `"first": true`, four result sentences and its checks. That its checks are judged on the ticket and not on a node, that its packet holds the registry's list and sections of the method, that its session may write the ticket, that its question is another question, that `show` then says "to be inducted", that it comes before every other vector and is left out for the simplest ticket: each is a case on `first === true` in the code. The test of REQ-GRAPH-004 compares the text literals of the folders `kit`, `graph` and `algorithms` with the names in the method's graph (`tests/graph.test.ts:221-229`); a mark in the place of a name passes it, and it does not read `src/flows`, where set-up names three nodes.
  3. *Source and termination.* From `src/method/graph.json` a reader cannot say what `write-code` rests on or writes: the vector holds `"function": {"term": "reference", "name": "write-code"}`; the registry's entry of that name holds `"writes": ["code"]`; what it rests on is in neither file. The graph file so holds nodes with their dependencies, and beside them a list of vectors that are joined to those edges only by a name in a second file.
  4. *Order from a list.* Within a term the next step is the first vector, in the order of the term's list, that is open (`next.ts:59-60`). The edges are used to refuse a list (`passes.ts:200-247`), not to give the order: design comes before tests in the default term because the registry's `default` lists it first, where the edges give no order between the two; and an induction whose term named steps outside the ticket's stretch cost two sessions before the run stopped (`C/ws/ta`: "the ticket's term composes" did not pass twice).
  5. The other places where structure is taken from something other than the edges are listed under check 4.
- **What depends on it.** Any graph but the shipped one. The product invites the user to edit `.stdo-builder/graph.json`; the user can change nodes, checks and vectors there, but not that there is exactly one first vector, that it writes a ticket with fields of these names, or what a change to the ticket reopens. And the owner cannot read from the graph file what a vector rests on, what it writes and what follows it, which REQ-GRAPH-004 says is declared there.
- **Smallest repair.** Make the ticket a node that the induction writes and the user accepts, and state in the graph, for each vector, the nodes it rests on and the nodes it writes.

### G-3. A governed session can give the product's own commands, which the instruction file set-up writes lists for it; a ticket it writes from its checkout starts a second event log and is later inducted and built as the user's words

- **Severity.** 3.
- **Reviewed.** `src/flows/setup.ts:157` and the block set-up writes into `AGENTS.md` and `CLAUDE.md` of the product (`C/ws/base/CLAUDE.md`), which every session started in the checkout is given; `packaging/INSTRUCTIONS.md:63-64`: "a block of the product's commands in `AGENTS.md` and `CLAUDE.md`, so that an agent started in the folder can run them for you." `src/algorithms/trespass.ts:98-100`: of the ticket lanes in the checkout, only the tickets that were there when the session started are protected. The commands `ticket` and `show` take a ticket's checkout for a workspace (items 1 and 2).
- **Claim it breaks.** The owner: "one event log! alternate event logs is a failure condition." Guard rail 1: "It controls the agent; the agent never controls it." `PRODUCT.md:123`: "There is one event log."
- **Evidence.**
  1. `C/ws/k9`. The scripted working session of `write-build` gave, in its checkout, `stdo-builder ticket . "Hello also prints the date. …"`. The product answered "The ticket 261123-173532-215e-hello-also-prints-the is written in the backlog" and exit code 0 (`C/out/k9/strayed.txt`). A second event log began at `C/ws/k9/.stdo-builder/local/checkouts/<ticket>/.stdo-builder/local/events.log` with the entry `ticket written`; the workspace's own log has no entry for that ticket being written. No protected file was reported. The ticket's file was committed with the step, went into main's backlog with the merge of the ticket's branch, and the next run pulled it (line 65), started an induction session on it (line 67) and asked the user: "Is the ticket inducted as you want it? … It rests on your words in the ticket, which are kept as you wrote them."
