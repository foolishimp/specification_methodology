What changed while a session worked, outside what its step writes, is the user's to rule on. This ticket repairs one finding of severity 2 from the review of release 3.2.0 and eight that follow from the same rule. The intent and the product definition are not changed by this ticket: guard rail 1 and the product definition's "The agent writes the product's assets and the framework writes its own files; neither writes the other's" already state the rule.

The rule. When a session starts, the framework takes the identity of every file of the product that git does not ignore, twice: as the ticket's checkout holds it and as the workspace's own folder holds it. When the session is over (REQ-FLOW-005), however it ended, it takes them again. What differs, outside what the step writes, is named to the user, file by file, with whether it was added, changed or removed. Until the user has ruled, the framework judges nothing on the ticket, commits nothing on it, starts no session on it and merges nothing: it reads no verdict, runs no check and does not commit what the step itself wrote. The run asks the user and ends as waiting, and `show` gives the question again. A yes means that each file named stands as it now is: the framework then commits them with the step, and whatever rests on them is judged or accepted again as after any change by hand. With a no the user puts back what is not to stand. The framework puts nothing back, in either case. The next run compares again, and asks again while a file differs that no yes was given on. What a step writes is what its packet's line "write" names: for a working session, the assets of its vector, and for the first vector the part of the ticket a session writes; for an evaluating session, its findings and its verdict, and nothing else. A verdict of an evaluating session that changed anything else is not read: after the ruling the evaluation is made again by a new session.

The same holds where a run was killed or cut off while a session was at work. The next run, once that session's processes are ended (REQ-FLOW-003, step 1), compares before it commits anything, in either folder: what is uncommitted in the workspace's own folder is not taken as "what the user changed by hand" before that. For this the identities taken at a session's start outlive the run: the framework keeps them, as identities and never as content, among its local files, from the session's start until the session's result is committed or ruled on. The index of identities it already keeps in each folder may serve, where nothing writes it between a session's start and the comparison. Where they are missing, the framework cannot tell what the session changed, says so, and goes on as it does now.

Where the product is one folder of a larger repository, the framework also notes, before and after the session, what git lists as changed or untracked outside that folder, in the checkout and in the repository's own folder, with each listed file's size and time of change, and the repository's branches, tags and stash. What differs there is named in the run's words, with the words that it changed while the session worked. It does not hold the ticket: other work goes on in such a repository, and the framework commits nothing there. This note is held by the run alone: after a killed run the next run says that it cannot tell what changed outside the product's folder. One thing holds it: the checkout is found on a branch that is not the ticket's. The run then names the branch and goes no further until the user has put it back.

The framework cannot tell who changed a file. So its words never say that the session changed it. They say that it changed while the session worked, and that it may have been the session or the user. What the framework itself writes in that time is not named, a ticket the user writes with the product's command among it.

Measured on this machine, with git alone. The identity of a whole working tree, with the user's uncommitted and untracked files and without what git ignores, is taken through an index of its own with no file's content written into git's store (`update-index --info-only`, `write-tree --missing-ok`). Two such identities are compared path by path by `git diff-tree -r --name-status`. `git for-each-ref` gives every branch, every tag and the stash. On the owner's repository, of which the product is one folder, 150,000 files are under git and 74,000 paths are changed or untracked, with 13 GB in them: git lists them in 3.6 seconds, and taking the identity of each one's content takes 51 seconds. That is why what lies outside the product's folder is compared by size and time, and REQ-PARAM-002 is to say how the framework's own time grows with the larger repository.

The limits, which are accepted. A file git ignores is not compared, the framework's own local files among them. Nothing outside the repository is seen. Whether a session read a file cannot be known. This is a check on an agent that strays and on a run the user interrupts; the framework is not hardened against an agent that sets out to get round it, as REQ-ALG-008 already says.
