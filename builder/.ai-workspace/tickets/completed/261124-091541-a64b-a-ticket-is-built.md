A ticket is built in the workspace's own folder, on a branch of its own: there is no second folder. This ticket repairs the two findings of severity 2 left from the review of release 3.2.0 (R-1 and R-2), two of severity 3 (R-9 and the third item of G-5), two of severity 4 (R-11 and R-16), and four small faults found while ticket 261124-001024-40f8 was built. The intent and the product definition are not changed by this ticket.

The rule. When a ticket becomes active, the framework commits the ticket's move to the active lane on the branch the folder is on, as now, makes the ticket's branch from that commit, and puts the folder on it. The ticket records the name of the branch it left. That branch is main for the ticket until the ticket is done: the framework reads its name from the ticket, and never again from the folder. Every session works in the workspace's own folder. While a ticket is active, a command that writes is refused unless the folder is on the ticket's branch; the refusal names both branches, and `show` still answers and says the same. When the ticket is done, its branch is merged into the branch it left, and the folder is on that branch again.

Why. Guard rail 2: "The workspace is mutable. The framework never freezes it, copies it or rebuilds it in order to work on it." The intent: "The agent does the work, in one workspace: the folder that holds the product being built." The owner, on 18 November 2026: "git, no copies!". Release 3.2.0 builds each ticket in a second checkout of the workspace, under `.stdo-builder/local/checkouts/`. Every tracked file is written there a second time, what git ignores (installed dependencies) is made again in each, and none is ever removed: in this workspace twelve of them hold 1.9 GB.

What follows from one folder:

1. What the user changes in the folder while a ticket is active is on the ticket's branch, and reaches main when the ticket is merged. Inside a larger repository the same holds for whatever is committed anywhere in that repository meanwhile, by the user or by anyone else who works in it: a repository's folder has one branch checked out. Two products in one repository cannot each hold an active ticket at the same time: no ticket is made active while the folder is on a branch the framework made for a ticket. The run is then refused and names the branch. The instructions say all of this in plain words; it is the cost of one folder.
2. The merge takes the whole tree of the ticket's branch. Main is first taken into the ticket's branch, in the folder; where the two collide the user decides, as now. Main is then an ancestor of the branch, so the merged content is the branch's own. The framework makes the merge commit from the branch's tree with both parents, moves main to it and puts the folder on main, with `git commit-tree`, `git update-ref` and `git symbolic-ref` alone. Measured on this machine (git 2.50.1): no file is written, no file's time changes, and what the user has uncommitted, staged or untracked is as it was. A plain `git switch main` at that point is refused by git where the user has an uncommitted change to a file that differs between the two branches, so the merge does not switch the working tree.
3. Where the branch the ticket left is checked out in another working tree of the repository when the ticket is to be merged, the run is refused and names that working tree. Git's own `git switch` refuses the same. Measured: the three commands of item 2 do not refuse, and they leave that other working tree showing the ticket's work as a staged change that takes it out again.
4. Where git refuses to take main into the branch because the user has uncommitted or untracked work in a file that main changed or added, the run is refused and names the files.
5. Main's content, where a check or an evaluating session's packet needs it, is read from git by commit and path, not from a folder.
6. The comparison of what changed while a session worked (REQ-ALG-008) is over the one folder. A question or a refusal names a file by its path in the workspace.
7. What the user leaves uncommitted in the folder and what a session that was cut off leaves there are now in one place. The requirements say how each is told from the other and committed, from the identities kept at a session's start (REQ-ALG-008) and from nothing else.
8. Where main, taken into the branch, changed a file of a node since the user answered on that node, the answer no longer stands and the user is asked again, whatever the file then holds (R-9).
9. In a clone: where the board holds an active ticket and the repository has that ticket's branch only as a remote branch, the run makes the local branch from it and puts the folder on it. Where it has no such branch at all, the run is refused and says so. The branch the ticket left is taken up in the same way, or the run is refused. It never begins the ticket again from main.
10. Where the folder is on no branch, no ticket is made active: the run is refused and says so.
11. The framework makes no checkout and prunes none. A checkout that an earlier release left is the user's to remove, with git's own command; the instructions say how, and how to remove a done ticket's branch. Where such a checkout still holds an active ticket's branch, git refuses to put the folder on it ("already used by worktree at <path>", measured). The run is then refused, names the checkout and gives the command that removes it.
12. A process the framework cannot place (REQ-FLOW-001) is then one whose current folder is the workspace's own folder, started after the session was, with no parent left alive. A job of the user's own that fits all three is named too; the instructions say so.
13. Several tickets at once (REQ-FLOW-009) stay Deferred. In one folder they would take turns; nothing of that is built here.
14. Scenario S13 has the user commit on main while the ticket is built. In one folder that commit is on the ticket's branch and reaches main with the merge; the scenario is rewritten to say so. The framework's own commits still take in files of the product's folder alone; the merge brings into main what was committed on the ticket's branch, and nothing else.

Bug items:

7. Severity 4. 8. Severity 4. The comparison counts the user's yes on what changed from the framework's own record alone. Where the ruling's line is no longer in the ticket, the record still counts it. By guard rail 3 the workspace is right: a yes counts only where the ticket holds its line and the record agrees.
9. Severity 5. `show` writes an index of its own, and trees into git's store, where REQ-ALG-012 says it keeps nothing. Either it writes nothing, or the requirement says what it writes and why.
10. Severity 5. Design decision D221 says that the run after a cut-off "goes on"; since ticket 261124-001024-40f8 it may wait for the user's ruling.

What stands. The framework deletes no branch and sends the history nowhere. It never decides which of two colliding changes is right. Guard rail 3: each step reads the workspace as it is now.
