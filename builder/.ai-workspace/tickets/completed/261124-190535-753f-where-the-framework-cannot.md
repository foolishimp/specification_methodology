Where the framework cannot tell what changed while a session worked, it asks the user: it never goes on. This ticket repairs the one finding of severity 2 from the review of the 3.2.1 candidate, V-1. The intent and the product definition are not changed by this ticket: guard rail 1 already states the rule.

What goes wrong. Since a ticket is built in the workspace's own folder, a session works in the folder that holds the framework's own local files, under `.stdo-builder/local/`, which git ignores. A session that removes what git ignores there removes with them the identities taken at its start and the run's hold. `git clean -fdx` and `git clean -fdX` do so, for a clean build, and `git stash --all` does so in passing. When that session returns, the run says "The framework cannot tell what changed … It decides nothing from their lack, and goes on", and commits everything in the folder, what the session changed outside its step among it. When the run is interrupted or killed instead, nothing is left to tell the next run that a session worked: it says nothing and commits it all as what the user changed by hand. In both cases a change to the graph's check, a line added to `AGENTS.md` and a stray file reached main with no ruling of the user. No intent to get round the framework is needed: the cleaning is an ordinary command.

The rule has two parts.

1. The identities kept from a session's start, and the hold a run keeps on a ticket, lie where git's cleaning does not reach: under git's own directory of the repository the workspace lies in, in a folder of the framework's own there. That directory is what `git rev-parse --absolute-git-dir` gives for the workspace's folder. Each workspace keeps its own apart, so that two products in one repository do not read each other's. Every word of the framework and of the instructions that names where the hold or the identities lie names the new place. Nothing else moves: the event log, what the sessions printed, the packets, what the checks found and the note of a ticket the user wrote with the product's command stay under `.stdo-builder/local/`. The same cleaning may remove any of those, and the index of identities with them; the comparison must not need any of them to be there, and the loss of any of them may lead to a question to the user but never to a commit with none.

2. Where the framework cannot tell all the same, it asks. After a session that returned or failed, where the identities from its start are missing, do not read, name a step the graph does not hold or name what git no longer holds, the identities of the commit the folder is on stand in their place, with nothing counted as what the step writes: each file not committed is put to the user, and nothing of the step is judged or committed until the user has ruled. That is what REQ-FLOW-003, step 1, already says of a run that was cut off; it now holds after every session. The run says in one sentence that the identities are missing and that it therefore asks about every file not committed. The words "It decides nothing from their lack, and goes on" go, from REQ-ALG-008, from the run's words and from the instructions; so does the acceptance line "The identities from a session's start are missing: it says so and returns nothing".
