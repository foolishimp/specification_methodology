A session is over when the framework has ended it. This ticket repairs one finding of severity 2 from the review of release 3.2.0 and six that follow from the same rule. The intent and the product definition are not changed by this ticket: guard rail 1 already states the rule.

The rule. A session is every process that the framework's start of the agent leads to: the agent's own process and every process started from it, in whatever process group or session of processes each then is. The framework knows them. While one of them is alive the framework starts no session on that ticket, judges nothing on it and commits nothing on it. The framework ends them when the agent's own process ends, which is the session's return; when the session's time is over; when the run receives the interrupt, the terminate or the hang-up signal; and, where a run was killed, at the start of the next run, before anything else is done on the ticket. It ends only a process it knows to be of the session. Where it cannot tell, it ends nothing, starts nothing, and names to the user what it found. Each time it ends processes it writes to the event log how many. A command of the product given from inside a session, on the workspace that session works for or on a folder inside it, is refused, says why and changes nothing.

The rule said "The framework knows them." It cannot know every one, and the rule was written before that was measured. Measured on this machine, which runs macOS: the system shows no environment for /bin/sh, /bin/zsh, /bin/sleep, /usr/bin/perl or a Node process that changed its title, so the mark alone misses each of them once it has left its parent. The system shows the parent and the process group of every process. `lsof -a -d cwd -p <numbers> -Fpn` gives the current folder of each of them. The shells a coding agent runs its commands in are /bin/zsh, each the leader of a session of processes of its own. The process module starts a child as the leader of a session of processes of its own unless it is told otherwise. About thirty real sessions on this workspace left no process behind.

So the framework knows a process of a session in three ways: by its parent, by its group and by its mark. What it has once known it knows until that process has ended. A process it cannot place, as REQ-FLOW-001 now defines it, it does not end: it names it, and the run is cut off. "Where it cannot tell, it ends nothing" means that it ends no process it does not know; the ones it knows it still ends. The limit that REQ-FLOW-001 states is accepted.

What stands of the build as it is, and is not to be rewritten: the mark and how it is read; the rounds that end processes; the signals; the hold; a file for each session's output; the refusal of the product's commands inside a session; and the run that is cut off where a session is not over.

What changes. First, the agent's own process, by its number and when it started, is known from the session's start, whether or not the system shows a mark for it. Second, a process is also known by its parent and by its group, the group read from the process table, and a process once known stays known through every round of the ending: one that loses its parent while it is being ended is still ended, and is counted only when it is gone. Third, at a session's end, and at the start of a run and in an answer where a cut-off run left its hold, the framework looks for a process it cannot place. It reads the current folder only of the few processes that pass the other tests. On Linux the current folder is what /proc gives. Fourth, tests of scenario S14's cases 8 to 10 and of each of the three ways, with a shell as the further process.

The framework does not watch the process table while a session is at work, and it keeps no new record: nothing is read from the event log, and the hold holds what it holds now.

Not in this ticket: that the library ends the process it runs in when a run is cut off. A later ticket carries it.
