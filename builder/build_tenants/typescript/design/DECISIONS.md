# Decisions of the build

Choices made where the requirements or the design are silent or ambiguous,
each the simplest reading within the intent's guard rails. Commentary for the
product owner's acceptance, not law.

## Where things are

- D1. *(How REQ-INTERFACE-001 is met, and what is not: D182.)* Layers, top down: `kit`, `graph`, `algorithms`, `services`, `flows`, `library`, `programs`. A module imports from its own layer or one above; an algorithm may use another (design §3: `open` is "by `passes`"). The services are carried out by kit modules (design §4); the library is the public surface; a program imports the library alone (REQ-INTERFACE-001).
- D2. `src/graph/` is the graph language (REQ-GRAPH-001 to 006). `src/method/` holds data only: the method's graph and registry.
- D3. `tests/` and `scripts/` sit beside `src/`, where the pinned `tsconfig.json` and `package.json` put them. Tests may import vitest, Node's own modules and the parts of Effect in §4; the import rules bind `src/`.
- D4. In the kit, C14 imports Effect's schema module alone; C1, C10 to C13 and C15 import the effect type and the one platform module each wraps; the rest import nothing of Effect. Deep paths only; the bare `effect` path is refused. Only C14 calls `JSON.parse`, `JSON.stringify` and the schema's decoders and encoders (design §4, §6).
- D5. Header of a module: `@carries Cn` in the kit; elsewhere `@uses` (entries of the set) and `@is` (requirement names). `@uses` names every entry the module imports directly and only entries reachable through its imports, except entries not yet built (design §6).
- D30. The checks of design §6 are `scripts/compliance.mjs`, tested by `scripts/compliance.test.mjs`. They read the set from design §1 and the requirements from their headings, and check `src/` and the headers of `tests/`. A graph module names a REQ-GRAPH requirement: the graph language is neither an algorithm nor a flow. The allowed Effect paths are those of §4 found in the pinned release; the bare package paths are refused. D42 lists the checks added with the flows.

## The graph language

- D6. Written form: JSON. A term is an object tagged by `term` (`session`, `sequence`, `workflow`, `reference`); the governing graph is a workflow; a registry is `{ "entries": [...] }` (REQ-GRAPH-001, 004, 005).
- D7. *(A `traced` check may declare another product's families: D83. `exists` goes, which leaves four: D187. How `traced` reads a requirement put off: D193.)* What runs a check is one of five kinds: `exists`, `command`, `ticket_field`, `ticket_kept`, `traced`. Any other kind is refused on reading (REQ-ALG-002, REQ-METHOD-002, 005).
- D8. *(A decision's condition: removed by D172.)* The verdict of a declared evaluation and the answer to a declared decision are read by `passes` as outcomes of their own; the graph does not list them among its checks (REQ-ALG-004, REQ-GRAPH-002).
- D9. The first vector's asset is the branch's ticket, which no node declares. Its identity is kept under the key `the ticket`, which no name can be: names have no white space (REQ-GRAPH-002, REQ-ALG-006).
- D10. *(Amended by D154: vector names too are unique across the graph.)* Node and vector names are unique in their workflow, node names across the graph (REQ-GRAPH-003).
- D11. A term that does nothing is an empty sequence or a workflow with no vectors. Constructors give the normal form (design C5).

## The services and the flows

- D32. C11 is a file holding the holder's process id, made by exclusive create; a hold whose process has ended is taken. "The OS releases it" is met by that check: after a kill the file remains and the hold does not (REQ-FLOW-003).
- D33. *(Git started in the workspace's folder, and main below the top of a larger repository: D201.)* C1 and C13 start git through C12, without the caller's git variables; no other module starts a process. The framework commits as "STDO Builder", with the user's hooks and signing off. A ticket's branch is `stdo/<ticket>`; main is the line the workspace's own checkout is on, `main` where set-up makes the repository; the done lane is the method's `completed` (REQ-FLOW-001, 004, 008).
- D34. *(`answers/` and `given/`: replaced by the resolutions in the ticket, D202 and D203. The question: no file holds it, D204.)* Tracked under `.stdo-builder/`: the settings, the graph and registry, `answers/<vector>.json`, `given/<vector>.json` (the identities a verdict was given on) and `.gitignore`. - D35. A ticket's name is the date and the time to the second, four characters of the identity of its text (C1) and its first four words, so names sort by when the ticket was written; two written in the same second sort by their identities (QA-09). `ticket` does not commit it; the next run commits what is uncommitted on main. The simplest ticket carries `- simplest: yes` (REQ-FLOW-003 step 1, REQ-FLOW-004).
- D36. *(What set-up records of the release of this product that is running: D197.)* Set-up writes the definition file before it installs the release (step 3 before step 2): the method's release manager, `stdo sync --definition <file>`, reads the release from it. It is started through C12 by the files service, the one write outside the workspace. The default release is v3.1.0-rc.2, the one this build was tested on (REQ-FLOW-002).
- D37. *(A verdict may also say `cannot`, D90; the packet, not the command, gives its form, D88; the answer on the first vector names its ticket, D200. An answer is no file: it is a `resolved user` line in the ticket, on the commit its delivery names, D202 and D203.)* A verdict is `{"verdict": "yes"}` or `{"verdict": "no"}` at the place the graph names; the default agent command says so, since the brief names only the place. An answer is `{says, reason?, on}`, on the identities as they are when the user answers (REQ-FLOW-005, 006).
- D38. *(An evaluation follows only where every check of its vector says yes: D173.)* A run commits what an interrupted step left before it takes main in, and judges it as it stands. It gathers main for `take_up`'s third rule only when the first two give nothing. An evaluation follows every working session, and otherwise only where no verdict stands. Any outcome that cannot be run, on an asset that is there, stops the run before a session (REQ-FLOW-003, 005; REQ-ALG-010).
- D39. *(What the answer flow reads in place of a gathered snapshot: D80.)* Whether the user is asked is one predicate, `asksUser`, beside `passes`; the step, the answer and `stands` use it. An answer of yes closes its vector, and the answer flow logs `vector closed`. The answer flow holds the ticket, so a run at work on it refuses the answer (REQ-FLOW-006, 007).
- D40. *(A run's exit 4 and the checkout's snapshot given to `stands`: superseded by D75 and D74.)* Exit codes: done and waiting 0, stopped 1, refused 2, a workspace that cannot be read or written 4; the words say what the user can do next. `stands` is given, for an active ticket, its checkout's snapshot and the changes `main...branch`; for a done ticket, what its merge brought (REQ-FLOW-003 laws, REQ-ALG-012).
- D41. *(Two more fixtures, `print` and `fails`: D81. What of REQ-VERIFY-002 the driver carries: D183.)* The stand-in is the second sessions layer, chosen by `run --stand-in <folder>`, so the settings stay as set-up wrote them. Its fixtures: `<vector>/<kind>/files/**` copied in, `append` added to the ticket, `seconds` to wait, and `gate` to wait for a file the driver makes. The driver builds `src/` alone (`tsconfig.build.json`, as `pnpm build` does) into the ignored `dist/`, and drives the command line alone. S9's code differs from S1's by a comment, as a new session's would; with the same bytes the old answer stands (REQ-VERIFY-002; S9).
- D42. Checks added to §6: the parts of Effect each kit entry and each layer may use; only C12 starts a process and only C1 and C13 start git; every exported flow is typed `Flow`, which names the seven services and no other; the library's exports name nothing of Effect; a program imports the library alone. An algorithm's `@uses` names the entries whose results it takes, by importing their types: `identity` and `trespass` C1's identity map, `stands` C10's fold step (design §2, §6).
- D43. A law shown by a test outside the case files is listed under `elsewhere` in its case file; the runner checks that test names it. REQ-ALG-001 law 1 and acceptance 1 are shown in `tests/kit_effects.test.ts`, in a new repository (REQ-VERIFY-004).

## Repairs after the first review

- D44. *(The event log judged as only added to, and the framework's own files that git ignores in the snapshots: superseded by D68.)* `trespass` is asked of two folders: the ticket's checkout, and main's own folder, which holds the graph, registry, settings and definition file the run reads. That reads the log twice per session, where design §5 says a run never reads it. Measured: 23 ms at 100 entries, 27 ms at 10,000, 76 ms at 100,000 (REQ-PARAM-002 allows under a second of growth).
- D45. *(What a verdict stands for is read under the commit its resolution names: D203.)* A verdict counts only where this step's evaluating session wrote it: the identities it is given on (`given/<v>.json`) are written only when the verdict file is there at the session's return and was absent at its start, or differs from it by identity, by when it was last written or by the node of the disk that holds it. That was not used: in REQ-FLOW-001's table of effects only an evaluating session writes a verdict, no effect of the framework removes a file, and the product definition says neither writes the other's. Comparing the file's stamp needs no new effect. A session that rewrites the same bytes within the same millisecond, in place, is read as not having written.
