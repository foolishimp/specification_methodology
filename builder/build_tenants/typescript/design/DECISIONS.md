# Decisions of the build

Choices made where the requirements or the design are silent or ambiguous,
each the simplest reading within the intent's guard rails. Commentary for the
product owner's acceptance, not law.

## Where things are

- D1. *(How REQ-INTERFACE-001 is met, and what is not: D182.)* Layers, top down: `kit`, `graph`, `algorithms`, `services`, `flows`, `library`, `programs`. A module imports from its own layer or one above; an algorithm may use another (design §3: `open` is "by `passes`"). The services are carried out by kit modules (design §4); the library is the public surface; a program imports the library alone (REQ-INTERFACE-001).
- D2. `src/graph/` is the graph language (REQ-GRAPH-001 to 006). `src/method/` holds data only: the method's graph and registry.
- D3. `tests/` and `scripts/` sit beside `src/`, where the pinned `tsconfig.json` and `package.json` put them. Tests may import vitest, Node's own modules and the parts of Effect in §4; the import rules bind `src/`.
- D4. In the kit, C14 imports Effect's schema module alone; C1, C10 to C13 and C15 import the effect type and the one platform module each wraps; the rest import nothing of Effect. Deep paths only; the bare `effect` path is refused. Only C14 calls `JSON.parse`, `JSON.stringify` and the schema's decoders and encoders (design §4, §6).
- D5. Header of a module: `@carries Cn` in the kit; elsewhere `@uses` (entries of the set) and `@is` (requirement names). `@uses` names every entry the module imports directly and only entries reachable through its imports, except entries not yet built (design §6).
- D30. The checks of design §6 are `scripts/compliance.mjs`, tested by `scripts/compliance.test.mjs`. They read the set from design §1 and the requirements from their headings, and check `src/` and the headers of `tests/`. A graph module names a REQ-GRAPH requirement: the graph language is neither an algorithm nor a flow. The allowed Effect paths are those of §4 found in the pinned release; the bare package paths are refused. D42 lists the checks added with the flows.

## The graph language

- D6. Written form: JSON. A term is an object tagged by `term` (`session`, `sequence`, `workflow`, `reference`); the governing graph is a workflow; a registry is `{ "entries": [...] }` (REQ-GRAPH-001, 004, 005).
- D7. *(A `traced` check may declare another product's families: D83. `exists` goes, which leaves four: D187. How `traced` reads a requirement put off: D193.)* What runs a check is one of five kinds: `exists`, `command`, `ticket_field`, `ticket_kept`, `traced`. Any other kind is refused on reading (REQ-ALG-002, REQ-METHOD-002, 005).
- D8. *(A decision's condition: removed by D172.)* The verdict of a declared evaluation and the answer to a declared decision are read by `passes` as outcomes of their own; the graph does not list them among its checks (REQ-ALG-004, REQ-GRAPH-002).
- D9. The first vector's asset is the branch's ticket, which no node declares. Its identity is kept under the key `the ticket`, which no name can be: names have no white space (REQ-GRAPH-002, REQ-ALG-006).
- D10. *(Amended by D154: vector names too are unique across the graph.)* Node and vector names are unique in their workflow, node names across the graph (REQ-GRAPH-003).
- D11. A term that does nothing is an empty sequence or a workflow with no vectors. Constructors give the normal form (design C5).

- D37. *(A verdict may also say `cannot`, D90; the packet, not the command, gives its form, D88; the answer on the first vector names its ticket, D200. - D40. *(A run's exit 4 and the checkout's snapshot given to `stands`: superseded by D75 and D74.)* Exit codes: done and waiting 0, stopped 1, refused 2, a workspace that cannot be read or written 4; the words say what the user can do next. `stands` is given, for an active ticket, its checkout's snapshot and the changes `main...branch`; for a done ticket, what its merge brought (REQ-FLOW-003 laws, REQ-ALG-012).
