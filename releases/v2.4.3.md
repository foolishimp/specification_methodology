## Product Delta

### Shared Versioned Toolchain Manager

STDO now carries an optional `stdo` command-line manager. It lets any number of
layout-neutral Product Definitions use complete immutable STDO cuts from one
shared versioned installation store rather than copying standards into every
project.

The manager provides:

- isolated reacquisition of annotated immutable RC tags;
- deterministic release manifests binding tag object, commit, repository
  tree, standards tree, complete standards inventory, member bytes, aggregate,
  plugin payload, license, and release note;
- atomic, read-only installation of each cut under one shared store;
- exact installation verification and portable `stdo:` URI resolution;
- synchronization of a Product Definition's already selected basis;
- separately presented and explicitly accepted Product Definition adoption;
- marker-bounded agent bootstrap management; and
- bounded status, verification, synchronization, adoption, and bootstrap
  operations across monorepos and hierarchical project fleets.

The Product Definition remains the sole authored selection surface. The store,
registry, installed manifest, resolver, cache, receipt, bootstrap block, and
CLI are derived mechanics. None may select a consumer basis or acquire
constitutional authority independently.

### Immutable RC And Version-Line Selector

Release identity now distinguishes:

- an immutable annotated `v<version>-rc.<n>` cut, which is the exact Product
  and replay identity;
- a mutable annotated `v<version>` version-line selector, which advertises the
  latest accepted RC on that line;
- a mutable `rc/<version>` construction carrier; and
- an optional mutable `release/<version>` convenience carrier aligned with the
  accepted selector.

Publishing a higher RC does not mutate an earlier RC and does not require a
minor-version increment. Exact-cut qualification and human acceptance precede
selector promotion. Moving the selector changes no consumer: each Product
Definition continues to pin one immutable RC URI and manifest digest until a
separate adoption transition is accepted.

### Product Definition Overlay Revision 3

The Product Definition Overlay schema identity is
`urn:stdo:schema:product-definition:3`. Its constitution now binds:

- `constitution.stdo.source.repository` — the release source;
- `constitution.stdo.selector` — a non-operative version-line discovery URI;
- `constitution.stdo.basis.uri` — the exact immutable installed RC URI;
- `constitution.stdo.basis.manifest_sha256` — the deterministic installed-
  release identity;
- `constitution.additional_authorities` — any non-STDO constitutional
  authorities;
- basis-qualified constitutional entrypoints; and
- one bootstrap entrypoint plus portable project-relative agent targets.

The schema keeps project identity, constitutional sufficiency, local axioms and
overrides, bounded-context disambiguation, reference-frame bases, `WHAT`, build
tenants realizing `HOW`, ticket and comment carriers, and explicit product
composition in the same layout-neutral overlay. The schema establishes
structural shape; the manager additionally performs URI syntax, exact-basis,
manifest, release identity, filesystem, target-confinement, and cross-file
checks within its declared boundary.

### Digest-Bound Adoption

Adoption is two separate invocations. A read-only plan binds the current
Product Definition bytes and basis to the resolved target RC, annotated tag
object, commit, tree, manifest, and candidate definition bytes, then emits a
deterministic `plan_sha256`. Mutation requires that exact externally accepted
digest and re-derives the plan before installation or write.

Selector, target, manifest, or Product Definition drift invalidates acceptance.
Fleet adoption applies the same rule with one aggregate digest over every exact
per-definition plan. Planning inside a mutating invocation cannot authorize
itself.

### Physical Store And URI Integrity

Store roots, registries, release directories, payload directories, and payload
files must be physical entries of their declared type. Symlinks, reparse
points, special entries, store redirection, missing entries, undeclared
entries, changed bytes, and URI traversal fail closed. Inventory covers every
filesystem entry type rather than silently ignoring non-file aliases.

Every `stdo:` locator is parsed before dispatch. URI-scheme case variation
cannot bypass the rule that a Product Definition schema and its operative basis
name the same immutable cut. A version-line selector must itself be an
annotated tag with a distinct peeled commit and must resolve to a matching
immutable RC tag.

### Bootstrap And Fleet Boundaries

Bootstrap targets resolve relative to `product.source_project`. Absolute
paths, parent traversal, redirected components, and boundary escape fail
closed. Fleet bootstrap additionally confines every source project to the
authorized fleet root and preflights every target before the first write.

The updater accepts exactly one correctly ordered marker span and preserves
every project-owned prefix and suffix byte. Appending a first span preserves
the existing file as an exact prefix.

Fleet discovery excludes declared VCS, dependency, generated, cache, virtual-
environment, build-output, and managed-store directory names. Directory
nesting creates no implicit product identity, inheritance, composition, or
authority.

### Quickstart And Stable Bootstrap

A version-neutral root `QUICKSTART.md` covers manager installation, immutable
cut installation, Product Definition creation, exact basis synchronization,
bootstrap, two-phase adoption, and fleet use. The root README links that route.

The large copied constitution formerly embedded in `AGENTS.md` and
`CLAUDE.md` templates is replaced with one equal, marker-managed discovery
bootstrap. It directs an agent to the applicable Product Definition, verifies
the exact installed basis, and loads owning sources. The bootstrap projects
authority; it does not restate or replace it.

### Candidate Review Repairs

The executable boundary incorporates the seven fail-closed repairs identified
during candidate review:

1. every mutating singular or fleet adoption requires an accepted plan digest;
2. schema-to-basis cut checks parse URI schemes case-insensitively;
3. physical store redirection and undeclared entry types are refused;
4. bootstrap writes are confined to the Product Definition and fleet roots;
5. marker order is validated and project-owned bytes are preserved exactly;
6. fleet discovery implements its declared exclusions; and
7. lightweight version-line selectors are refused.

Each repair has a positive refusal-path regression.
