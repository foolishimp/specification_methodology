## Release-Framework Repair

### Defect

After RC2 publication, the mutable `v2.4.3` selector and `release/2.4.3` branch
still named RC1. A consumer asking for the `2.4.3` channel could therefore be
offered an older cut and, if it accepted that plan, could be downgraded within
the same release line.

The immediate mutable carriers were advanced to RC2 without moving either
immutable RC tag. This cut makes that repair durable in release law, resolver
behavior, operator guidance, and regression evidence.

### Release Identity

Release publication now distinguishes:

- `v<version>-rc.<n>` — one immutable, annotated, exactly addressable RC cut;
- `v<version>` — the mutable, annotated selector for the greatest positive RC
  ordinal published on that version line;
- `rc/<version>` — the mutable candidate carrier; and
- `release/<version>` — an optional mutable branch aligned to the same latest
  published RC commit as the selector.

The version-line selector is equivalent to `v<version>-rc.latest`. Publishing a
higher RC advances the selector and optional release branch as one publication
transaction. Acceptance remains a verdict over an exact immutable RC and does
not move the selector or create a second final carrier.

The release sequence is now explicit:

1. triage and construct the bounded candidate;
2. reconcile release-scoped bytes and run pre-RC checks;
3. commit the exact carrier;
4. create the next annotated immutable RC tag and an annotated version-line
   selector over the same commit;
5. atomically publish the carrier, RC branch, immutable tag, selector, and
   optional release branch where the transport supports it;
6. verify remotely that the selector and optional release branch name the
   highest published RC commit;
7. qualify and accept the exact immutable cut; and
8. let each consumer separately review and accept its own digest-bound adoption
   plan.

A published higher RC with a lagging selector is an invalid fail-closed state,
not authority to keep resolving the older cut.

### Resolution And Adoption

The toolchain manager now:

- enumerates every well-formed immutable RC tag on the selected version line;
- selects the greatest ordinal numerically;
- requires both that RC and the version-line selector to be annotated tags
  peeling to the same commit;
- identifies and refuses a missing, lightweight, lagging, or mismatched
  selector;
- refuses channel adoption when its target is below the Product Definition's
  current exact basis on the same line; and
- preserves direct installation and `sync` of every explicitly selected older
  immutable cut.

Consumer selection remains explicit. Moving the selector never edits a Product
Definition. `adopt --dry-run` presents an exact plan; mutation requires the
externally accepted plan digest and re-derives it unchanged. A consumer that
intentionally stays on an older cut names its exact release URI and manifest
digest and uses exact-basis operations rather than the latest channel.

### Toolchain Patch

The subordinate manager version is `stdo-toolchain 0.1.1`. Its executable delta
is confined to highest-RC channel resolution, release-coordinate comparison,
same-line downgrade refusal, and positive refusal-path tests. All RC2 store,
manifest, URI, schema, bootstrap, fleet, plan-acceptance, and physical-boundary
law is conserved.

## Conserved Method And Product

`STDO` remains explicitly defined as **Specification, Ticketing, Design,
Outcome-Driven Development**. The acronym's owning clause and glossary locator
are conserved.

This cut changes no Product outcome, construction algebra, reference-frame
family, bounded-context identity, Product Definition schema shape, installed
manifest shape, testing frame, composition rule, build-tenancy rule, or
authority relation. `PRODUCT.md` changes only its selector-description
projection so it names the highest published immutable cut rather than an
accepted available cut.

## Exclusions

This release adds no:

- silent consumer upgrade or mutation without an accepted exact plan;
- implicit selector following by `sync`;
- rollback permission for the version-line selector;
- removal or rewriting of an earlier immutable RC tag;
- required minor-version increment for a bounded RC repair;
- new Product Definition or installed-manifest schema revision;
- project-local standards installation requirement; or
- Product, runtime, semantic, ticketing, build, or assurance engine.
